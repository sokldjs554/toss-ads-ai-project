# 라벨링 가이드라인 v1.0

> **먼저 밝혀 둘 것: 이 프로젝트에는 독립 라벨러가 없다.** 기존 평가셋은 구현 작성자의 라벨이며(`evals/datasets/PROVENANCE.json` 참고), 별도 AI 작성자의 합성 사례도 독립 사람 검증은 아니다.
> 이 문서의 파이프라인(검수 대기열 → 라벨 → 일치도 → 조정 → 평가셋 후보)과 서버 공동 검수의 계정·권한·저장은 구현했지만 실제 독립 사람의 라벨은 확보하지 않았다. 일치도 등의 값은 **합성 예시**
> (`evals/datasets/labeling_demo.jsonl`, 가상의 라벨러 둘 + 조정자 하나)로 잰 것이며 실제 라벨러 합의 수준이나 "독립 라벨러를 확보했다"는 근거가 아니다. 서로 다른 접근키 계정도 실제로 서로 다른 사람임을 증명하지 않는다.
> 이 문서의 기준값(kappa 0.60, 검증용 정확도 80%, 표본 30건 등)은 모두 **이 프로젝트가 가정한 값**이다 — 외부 표준이나 실측으로 정한 것이 아니다.

코드: `ops/review_queue.py`(대기열) · `ops/labeling.py`(라벨 검증·일치도·조정·품질) · `ops/dataset_tools.py`(평가셋 내보내기·검증) · `ops/prelabel.py`(사전 라벨) · `ops/team_review.py`·`ops/team_review_store.py`(서버 공동 검수) · 화면 `ui/review_queue_view.py`·`ui/team_review_view.py`.

**구현과 운영 연결 상태.** 서버 DB 기능은 소스 `fc8724d`의 [CI 39570494115](https://github.com/sokldjs554/toss-ads-ai-project/actions/runs/39570494115)에서 PostgreSQL 검사 **38개**와 전체 테스트 **4,281개·252.09초**를 통과했다. 실제 운영 DB의 초기화·연결은 **최종 사용자 승인 대기**이며 활성화한 공동 공간은 **0건**이다. 실패한 초기화 뒤 해당 공동 검수용 스키마·역할이 남지 않았음을 확인했고, 비밀값을 포함하는 DB 계정 생성의 후속 동작은 자동 승인 검토에서 거절되어 실행 0건이다. 승인 전 실제 DB 변경·서버 환경 설정을 하지 않는다. 실제 독립 사람의 제출도 **0건**이며 화면·CI 결과를 검수자의 참여나 운영 연결 완료로 표시하지 않는다. 현재 상태는 [OPERATIONS.md](OPERATIONS.md) §6.7, 키 발급·교체·복구 절차는 [TEAM_REVIEW.md](TEAM_REVIEW.md)를 따른다.

공개 배포의 기준 코드 `3e52e58`은 Pages·Render와 CI 완료를 확인했다. 별도 Cloud Browser의 기본 TLS 검증을 유지한 **제한된 공개 데스크톱 관측**에서 공동 검수의 DB 미설정 안내를 확인했으며, 실제 검수 계정의 저장·제출을 검증한 것은 아니다. [공개 화면과 관측 범위](evidence/remaining-20261021/public-cloud-3e52e58/README.md). 로컬 185개 검사와 공개 전체 185개 검사의 미실행 상태를 구분하고, 이후 문서·증거 커밋을 관측 기준 코드와 섞지 않는다. 활성화에 필요한 구체적인 사용자 승인 범위는 [DB 활성화 계획](deployment/team-review-neon-activation.md)에 있다.

## 1. 흐름

```
담당자 확인 건 ─▶ 대기열(queued) ─▶ 점유(claimed) ─▶ 라벨(labeled) ──────────────▶ 내보내기(exported)
 (+무작위 점검 표본)                                   └▶ 갈림(disagreed) ▶ 조정(adjudicated) ▶ ┘      (건너뜀: skipped)
```

- 실행 결과에서 가져올 때에는 **'담당자 확인 필요'로 끝난 광고만** 들어간다(`enqueue_from_run`). 같은 실행의 같은 광고안은 두 번 들어가지 않는다. 공동 검수의 관리자는 별도로 광고 문구·상품 사실·랜딩 문구를 직접 입력할 수 있고, 그때 출처 ID와 합성 여부를 명시한다. 화면의 합성 예시 선택은 기본으로 켜져 있다.
- 먼저 볼 광고는 **불확실성 표집**으로 정한다 — 검토 모델의 확신이 낮을수록, 두 모델 계열의 판단이 갈릴수록, 금융처럼 주의가 필요한 업종일수록, 코드 판정과 합쳐진 판정이 다를수록 먼저.
  `priority = 0.45×(1−확신) + 0.20×[교차 확인 불일치] + 0.20×업종 위험도 + 0.15×[코드≠합쳐진 판정]` (0~1). 가중치·업종 위험도(대출·투자·가상자산 1.0 … 커머스·앱 0.2)는 가정한 값이다.
- 마감(SLA)은 우선순위 구간별로 4시간(≥0.6) · 24시간(≥0.3) · 72시간이다. 마감이 1시간 안으로 다가왔거나 지난 광고는 우선순위보다 먼저 배정된다. 실제 운영 기준이 아니라 가정한 값이다.
- 점유는 30분 뒤 만료되고, 라벨러 식별자 하나가 동시에 잡을 수 있는 광고는 3건까지이며, **같은 식별자가 같은 광고를 두 번 라벨할 수 없다.** 공동 검수에서는 서버가 접근키 계정 ID를 사용한다. 한 사람이 여러 계정을 갖는 것까지 검증하는 신원 확인 기능은 없다.
- 라벨이 갈리면(판정이 하나라도 다르면) 제3의 조정자가 최종 라벨을 정한다. 공동 검수에서는 그 광고를 라벨한 계정의 조정을 서버가 거절한다.

### 개인 저장과 서버 공동 검수

| 경로 | 저장·접근 범위 | 담당자와 복구 |
|---|---|---|
| 운영 › 검수 대기열 | 같은 사이트 주소·브라우저 프로필의 IndexedDB. 계정 인증이 적용되지 않는 개인 작업 공간 | 직접 입력한 라벨러 식별자. 저장 완료 후 성공 표시, 탭 충돌·저장 실패 때 편집 중지와 전체 JSONL 백업·복구 |
| 운영 › 공동 검수 | 서버 PostgreSQL의 소규모 공동 공간. 계정·대기열·라벨·요청 영수증을 JSONB 한 행에 저장하고 행 잠금으로 변경을 직렬화 | 서버가 접근키의 계정·역할·배정을 확인. 저장 응답이 불확실하면 같은 요청 ID·내용으로 확인 |

두 저장소는 자동으로 합쳐지지 않는다. 개인 백업을 업로드해 공동 상태를 덮어쓰는 기능도 없다. stlite 브라우저 실행판은 공동 검수의 서버 링크를 안내하며, 서버 DB가 미설정이면 설정 필요 안내를 표시한다. 공동 검수의 인증은 이 공간에만 적용하고 전체 공개 앱의 SSO·API 인증까지 제공하지 않는다.

공동 검수의 **검수자**는 본인에게 배정된 광고를 읽고 제출·반납한다. 다른 검수자의 판정·사전 라벨은 제출 뒤에도 보이지 않는다. **조정자**는 본인이 라벨하지 않은 갈림을 읽고 조정하며 내보낼 수 있다. **관리자**는 계정 발급·키 교체·비활성화, 광고 추가·내보내기를 수행한다. 이름·역할·담당자 ID를 화면에서 임의로 바꾸어 권한을 얻을 수 없다.

접근키는 비밀번호형 입력으로 받고 UI 세션에만 보관하며 로그아웃 때 지운다. 서버에는 키 해시만 저장하고 새 키는 발급 확인 뒤 한 번 표시한다. 응답 유실·저장 장애는 같은 요청을 보존하지만, 원자적으로 거절된 잘못된 라벨은 이유를 표시하고 고칠 수 있다. 회수·만료된 키는 로그아웃·새 키 입력으로 복구한다. 세션을 잃으면 미확인 요청도 복원되지 않으므로 서버의 본인 배정·계정 상태부터 확인한다. 실패별 절차는 [OPERATIONS.md](OPERATIONS.md) §6.7을 따른다.

## 2. 라벨 스키마 (`Annotation`)

| 필드 | 내용 |
|---|---|
| `item_id` | 대기열 항목 id |
| `annotator` | 개인 도구에서는 라벨러 식별자(1~40자). `pipeline`·`system`·`model` 등 자동 처리용 이름은 거부한다. 공동 검수에서는 서버가 인증한 계정 ID로 채우며 클라이언트가 지정할 수 없다 |
| `decision` | `APPROVE`(점검 통과) · `REVISE`(수정 필요) · `REJECT`(게재 불가). **'담당자 확인'은 라벨이 아니다** |
| `rule_ids` | 판정의 이유가 된 규칙. `guardrails/policy.yaml` 카탈로그 안의 id만 |
| `cited_spans` | 문제가 된 구절. **광고 문구에 글자 그대로** 있어야 한다 |
| `rationale` | 이유 (최대 2000자) |
| `seconds_spent` | 처리 시간. 비워 두면 큐가 점유 시각부터 잰다 |
| `guideline_version` | 이 라벨을 단 가이드라인 판본 (현재 `1.0`) |
| `prelabel_mode` / `prelabel_decision` | 자동 제안을 **보여 줬는지/숨겼는지**와 그때의 제안 — 큐가 채운다 |
| `flags` | 큐가 채운다. 예: `too_fast`(읽을 수 없을 만큼 빠른 제출) |

코드가 라벨을 **받지 않는** 경우(저장되지 않고 이유가 화면에 나온다):

1. `REVISE`/`REJECT` 인데 규칙이 하나도 없음.
2. `REVISE`/`REJECT` 인데 인용한 구절이 하나도 없음 — 단, 아래 '빠진 내용' 유형의 규칙만 골랐다면 인용 없이 이유(10자 이상)로 대신한다.
3. `APPROVE` 인데 게재 불가(block) 등급 규칙을 골랐음.
4. 카탈로그에 없는 규칙 id.
5. 인용한 구절이 광고 문구(제목·본문·버튼·안내 문구 한 줄 안)에 **그대로 없음** — 공백이나 표기를 맞춰 주지 않는다.
6. 인용이 2자 미만이거나 200자 초과, 20개 초과.

경고만 하고 받는 경우: `APPROVE` 인데 수정 필요(fix) 등급 규칙이 있음 · `REJECT` 인데 게재 불가 등급 규칙이 없음 · `REVISE` 인데 게재 불가 등급 규칙이 있음 · `too_fast`.
`too_fast` 기준은 `max(3초, 문구 글자 수 ÷ 20)` 이다(`ASSUMED_READ_CHARS_PER_SEC`). 실제 읽는 속도를 잰 값이 아니라, 이보다 빠르면 물리적으로 읽기 어렵다고 본 가정이다. 제출을 막지 않고 표시만 한다.

**'빠진 내용' 유형 규칙**(인용할 구절이 없는 규칙): `TA-OMISSION-01`(혜택 조건 생략), `GRND-COND-01`(상품 정보의 조건이 빠짐), 그리고 필수 고지 누락 규칙(`FIN-DISCLOSE-*`).
없는 것을 인용할 수는 없으므로, 이 규칙만 고른 경우에는 **무엇이 빠졌는지** 이유에 적는다.

## 3. 판정 기준과 경계 사례

판정 기준은 `docs/POLICY.md` 와 `guardrails/policy.yaml` 의 규칙 등급을 따른다. **이 기준은 이 프로젝트가 공개 자료로 재구성한 검사 기준이며 실제 플랫폼 심사가 아니다.**

| 판정 | 뜻 | 대표 사례 (데이터셋 id) |
|---|---|---|
| `APPROVE` 점검 통과 | 규칙에 걸리는 구절이 없고, 필요한 고지·조건이 있다 | G-060(범위 금리 + 심사 조건 병기), G-065(우대 조건 병기), G-070(속도 표현 + 조건 병기), K-A3(같은 금액의 다른 표기 `5만원` = `50,000원`) |
| `REVISE` 수정 필요 | 고치면 쓸 수 있다 — 조건 생략·표기 오류·필수 고지 누락 같은 fix 등급 | G-053(랜딩 페이지에 쿠폰 조건이 없음), G-069(자동결제 조건 누락), K-A1(고지 문구의 금액이 사실과 다름), G-043(한도 단정 + 대출 고지 누락) |
| `REJECT` 게재 불가 | 그대로는 게재할 수 없다 — block 등급 | G-001(무심사·당일 입금 등 불법 대부광고 전형), G-002(원금 100% 보장), G-009(사행심 조장), G-014(리볼빙을 부담 없는 결제로 표현) |

### 경계 사례 — 같은 문구, 다른 라벨

- **G-053 ↔ G-068**: 제목·본문·버튼이 같다. G-053 은 랜딩 페이지에 쿠폰 조건이 없어 `REVISE`(TA-LANDING-01), G-068 은 랜딩 페이지가 사실과 같아 `APPROVE`. 광고 문구만 보지 말고 **랜딩 페이지 글·상품 정보**를 함께 본다.
- **C-069-A ~ D (G-069 대조 사례)**: `최초` 표현이 있든 없든 **결제 조건이 빠진 쪽만** `REVISE`(GRND-COND-01), 조건을 쓴 쪽은 `APPROVE`. 판정의 원인이 '최초'가 아니라 결제 조건임을 대조로 확인했다.
- **K-A1 ↔ K-A3**: 사실은 `50,000원 이상`. 고지가 `5,000원 이상`이면 `REVISE`(K-A1), `5만원 이상`이면 같은 금액의 다른 표기라 `APPROVE`(K-A3).
- **G-060 / G-070 같은 '무서운 단어가 있는 정상 광고'**: `대출`·`당일 입금`이 있어도 범위 금리·심사 조건·필수 고지를 갖췄으면 `APPROVE`. 단어가 아니라 **조건과 고지**를 본다.

### 규칙 id 고르는 요령

1. **가장 직접적인 규칙 하나**를 먼저 고르고, 같은 구절이 다른 규칙에도 해당하면 더한다(예: 무심사 + 당일 입금 → `FIN-APPROVAL-01` + `FIN-SPEED-01`).
2. 필수 고지가 빠졌으면 해당 업종의 고지 규칙(`FIN-DISCLOSE-LOAN-01` 등)을 고른다. 이 규칙은 인용 없이 이유로 대신한다.
3. 규칙 등급과 판정을 맞춘다 — block 등급이 하나라도 있으면 보통 `REJECT`, fix 등급만 있으면 `REVISE`. 어긋나는 라벨(예: fix 등급뿐인데 `REJECT`)은 **더 엄격한 쪽을 고른 이유**를 이유란에 적는다.
4. 화면에는 규칙의 이름만 보인다. 규칙 코드는 상세 기록과 내려받는 파일에만 있다.

### 인용 규칙

- 광고 문구에서 **그대로 복사**한다. 화면의 후보(제목·본문·버튼·안내 문구의 한 줄과 그 문장·쉼표 조각)에서 고르면 항상 통과한다.
- 한 구절은 한 문구 단위(제목이면 제목 안) 안에 통째로 있어야 한다. 제목 끝과 본문 앞을 이어 붙인 구절은 광고에 없는 문장이므로 거부된다.
- 보이지 않는 문자·띄어쓴 글자로 우회한 광고는 화면에 보이는 모양과 실제 글자가 다를 수 있다. 직접 입력이 거부되면 후보에서 고른다.

### 애매할 때

**'담당자 확인'으로 도망가지 않는다.** 라벨의 선택지는 세 개뿐이다.

1. 두 판정 사이에서 망설여지면 **더 보수적인(엄격한) 쪽**을 고른다: `REJECT` > `REVISE` > `APPROVE`.
2. 왜 망설였는지 **이유란에** 적는다(무엇과 무엇 사이였는지). 이 메모가 일치도 점검과 가이드라인 개정의 재료가 된다.
3. 규칙 문서에 답이 없는 새 유형이면 이유에 적어 두고, 개정 후보로 모은다(아래 '가이드라인 개정').

## 4. 자동 제안(사전 라벨)과 앵커링

자동 검사의 판정을 **제안**으로 미리 보여 줄 수 있다. 제안은 `Annotation`이 아니고, 사람이 직접 확인해 제출해야 라벨이 된다(자동 확정 금지). 제안을 보면 그 제안에 끌려가는 편향(앵커링)이 생길 수 있어,

- 개인 검수 화면의 기본값은 **제안 숨김**이다. 먼저 직접 판단한 뒤 필요하면 켜서 비교한다. 서버 공동 검수의 검수자 경로는 항상 숨기며, 다른 검수자의 판정도 반환하지 않는다.
- 라벨마다 제안을 보여 줬는지/숨겼는지(`prelabel_mode`)와 그때의 제안(`prelabel_decision`)이 기록된다.
- `ops.prelabel.anchoring_report` 가 두 집단이 제안과 같은 판정을 낸 비율을 비교한다. 두 집단의 광고·라벨러 구성이 같지 않으면 앵커링의 증거가 아니고, 집단마다 20건 미만이면 비교하지 않는다.

## 5. 가이드라인 버전 관리

- 판본은 `ops/labeling.py` 의 `GUIDELINE_VERSION` 하나이고, **라벨마다 어느 판본으로 달았는지** 남는다(`guideline_version`). 평가셋 행에도 같은 필드가 들어간다.
- 판정 기준을 바꾸면 판본을 올리고, 이 문서 맨 위 제목과 아래 변경 이력에 이유를 적는다. 판본이 다른 라벨을 한 일치도 계산에 섞지 않는다(섞어야 하면 먼저 같은 판본으로 다시 라벨한다).
- 변경 이력: **v1.0** — 첫 판. 코드의 규칙 등급(block/fix/warn)을 판정 기준으로 삼고, 애매하면 보수적으로 라벨하는 원칙을 정함.

## 6. 라벨러 교육과 검증용 항목

아래 검증용 항목·라벨러 품질 도구는 기존 개인 대기열에서 제공한다. 공동 검수 UI는 계정별 배정·제출·갈림 조정에 집중하며 검증용 풀 설정이나 앵커링 실험 화면을 제공하지 않는다.

1. **교육**: 이 문서의 경계 사례(3절)를 읽고, 데이터셋 사례 몇 건을 직접 라벨해 본다. 이때 자동 제안은 숨긴다.
2. **검증용 항목(gold)**: 정답을 아는 광고를 일반 광고와 **같은 모양**으로 섞는다(기본 약 10%, 해시로 정한 자리). 라벨러에게는 어느 것이 검증용인지 보이지 않고, 큐가 내주는 화면용 데이터(`AnnotatorView`)에는 검증용 여부·정답이 들어갈 자리가 없다. 단서가 될 만한 것도 같은 모양으로 맞춘다 — 점유한 광고의 사유 문구는 모든 광고에 같은 말이고, 상품명·광고안 id·어조는 보이지 않으며, 점유한 광고는 대기 목록에서 빠진다(검증용 항목은 처음부터 목록에 없으므로 '목록에 있던 광고인가'로 가릴 수 없다). 같은 검증용 항목은 라벨러마다 한 번만 나가고, 반납해도 같은 사람에게 다시 나간다(피할 수 없다). **다만** 검증용 풀을 만들고 가이드라인을 쓴 사람이 곧 라벨러인 이 프로젝트에서는 블라인드가 이름뿐이다 — 이 장치는 라벨러와 관리자가 다른 사람일 때 의미가 있다.
3. **판단**: 검증용 항목을 5건 이상 라벨한 뒤에야 정확도로 본다(미만이면 '표본 부족'). 정확도가 80% 미만이면 '주의' — 사람을 평가하는 신호가 아니라 **가이드라인·교육·표본을 점검하라는 신호**다. 보조 지표: 확정 라벨과 다르게 낸 비율(30% 초과 시 주의), 평균 처리 시간, `too_fast` 건수.
4. **한계**: 검증용 항목의 정답도 가이드라인 작성자의 라벨이다. 정확도는 '작성자 기준과의 일치'이지 '진실과의 일치'가 아니다. 검증용 항목은 이미 기존 평가셋(golden 등)에 있는 광고라서 **평가셋 후보로 내보내지 않는다**(코드가 제외한다).

## 7. 일치도와 조치

계산 함수와 아래 일치도 화면은 기존 라벨링 도구의 기능이다. 공동 검수자는 다른 사람의 판정이나 집계 일치도를 받지 않으며, 이 기능을 근거로 공동 검수에 실제 사람의 합의 측정값이 생겼다고 주장하지 않는다.

- 같은 광고를 둘 이상이 따로 라벨해야 잴 수 있다. 라벨러가 한 명이면 화면이 "라벨러가 한 명이라 일치도를 잴 수 없습니다"라고 알린다.
- 두 명이면 Cohen's kappa, 세 명 이상이면 Fleiss' kappa(사람 수가 같은 항목끼리)를 쓴다. 함께 일치율, 판정 혼동 표, **규칙별 일치도**를 본다.
- **표본이 적으면**(공통 항목 30건 미만) '표본 부족' 경고와 함께 부트스트랩 95% 신뢰구간(재표집 1000회, 시드 고정)을 낸다. 구간 너비가 0.4 를 넘거나 한 가지 라벨이 90% 이상이면 그 경고도 낸다.
- Landis-Koch 해석 띠(0.20 이하 거의 없음 … 0.80 초과 거의 완벽)는 **참고용 관례**다.
- **조치 기준(가정)**: kappa < 0.60 이면 가이드라인을 개정한다. 절차: ① 판정이 갈린 광고와 조정 이유를 모은다 ② 같은 갈림이 반복되는 유형을 규칙·경계 사례로 문서에 추가한다 ③ 판본을 올린다 ④ 갈린 광고를 새 판본으로 다시 라벨해 일치도가 나아졌는지 본다. 신뢰구간이 기준(0.60)을 걸치면 '개정이 필요하다고도, 필요 없다고도 말할 수 없다'로 읽는다.
- kappa 는 라벨러끼리 같은 가이드라인을 같은 뜻으로 읽었는지를 보여 줄 뿐이다. **라벨이 옳다는 뜻이 아니고**, 두 사람이 같은 오해를 공유해도 높게 나온다.

## 8. 조정(adjudication)

- 라벨의 판정이 하나라도 다르면 `disagreed` 가 되고, **그 광고를 라벨하지 않은** 조정자가 최종 판정·규칙·인용·이유(10자 이상)를 남긴다. 처음 라벨들은 지워지지 않고 남는다.
- 조정은 다수결이 아니다(세 명 중 둘이 같아도 조정을 거친다). 조정 이유는 가이드라인 개정의 재료다.
- 라벨이 일치한 경우 최종 규칙은 라벨러들이 **공통으로 고른 규칙**이고, 공통 규칙이 없으면 합집합을 쓰고 '규칙 선택이 라벨러마다 달랐음'을 메모에 남긴다.

## 9. 평가셋으로 내보내기

`ops.dataset_tools.export_rows(items, guideline_version=..., split_seed=...)`:

- **라벨이 확정된 것만**(일치 또는 조정). 한 명만 라벨한 것은 기본으로 제외하고, 포함하려면 명시해야 하며 행에 `single_labeler: true` 가 붙는다. **합성 예시와 검증용 항목은 제외**한다.
- 행의 필드는 `evals/datasets/golden.jsonl` 첫 행의 필드(`id`·`category`·`headline`·`body`·`cta`·`label`·`rule_ids`·`disclosures`·`facts`·`claims`·`landing_text`·`difficulty`·`notes`·`source`·`split`)를 그대로 따르고, 출처 필드(`labelers`·`adjudicated`·`agreement`·`rule_agreement`·`single_labeler`·`synthetic`·`guideline_version`·`queue_item_id`)가 뒤에 붙는다. `difficulty` 는 조정을 거친 광고는 `gray`, 나머지는 `unrated`(난이도를 따로 라벨하지 않았다).
- **분할은 문구 해시로 안정 배정**한다 — 제목·본문·버튼을 정규화(전각·한자·보이지 않는 글자·공백·대소문자 접기)한 키와 고정 시드(`preflight-split-v1`)의 해시가 0.2 미만이면 `holdout`, 아니면 `dev`. 같은 문구는 언제나 같은 분할이고, 새 항목이 이미 있는 항목의 분할을 바꾸지 않는다. 해시는 확률적이라 표본이 작으면 20%가 정확히 지켜지지 않는다. **최종 확인용(holdout)은 이 규칙을 고정한 뒤에 만들고, 결과를 보고 분할을 바꾸지 않는다.**
- `validate_dataset(rows, existing=...)` 가 스키마, 라벨-규칙 일관성, id 중복, 같은 행인데 라벨이 다른 경우, **근접 중복**(정규화한 제목·본문·버튼의 글자 3-gram 자카드 ≥ 0.8; 400건을 넘으면 MinHash 샤드로 후보를 추림)과 **개발용↔최종 확인용 누수**(근접 중복 쌍이 서로 다른 분할에 걸림)를 점검한다. 근접 중복은 막지 않고 경고한다 — 글자 모양의 유사도라서 뜻이 같은 다른 표현은 잡지 못하고, 조건 숫자만 다른 대조 쌍은 잡는다.
- **기존 파일을 덮어쓰지 않는다.** 내보내기 결과는 새 파일이다(`write_jsonl_new` 는 이미 있는 파일이면 거부). 평가셋에 합치기 전에 위 검증을 돌리고 사람이 확인한다.

**서버 공동 검수의 추가 제한.** 관리자·조정자만 내보낼 수 있고, `allow_single_labeler=False`, `required_labels=2`를 서버가 고정한다. 두 계정의 라벨이 일치하거나 해당 항목을 라벨하지 않은 제3 계정이 이견을 조정한 자료만 후보가 된다. 합성 자료는 기본 제외하며, 포함을 명시한 경우 파일에도 그 여부가 남는다. 내보내기에는 `identity_verified=false`, `independence_verified=false`를 유지한다. 두 계정이라는 조건은 실제 독립 사람 두 명을 확보했다는 증명이 아니며, 평가셋 편입 전에 실제 참여자·검토 방식·출처를 별도로 확인해야 한다.

### 평가셋 라벨 변경 절차 (`label_history`)

평가 결과를 보고 라벨 오류가 의심되면(예: G-069 — 초기 라벨 `APPROVE` 를 대조 사례와 모델 결과를 본 뒤 `REVISE` 로 고침):

1. `python -m ops.dataset_tools --suspects` 로 '코드·모델이 높은 확신으로 라벨과 다르게 판정한' 사례를 점수순으로 본다. 이것은 **다시 볼 후보**일 뿐 라벨이 틀렸다는 판정이 아니다 — 라벨·규칙·모델 중 어느 쪽이 틀렸는지 사람이 원문을 다시 읽어 정한다.
2. 라벨을 바꾸기로 하면 `revise_label(row, new_label=..., new_rule_ids=..., reason=..., guideline_version=...)` 로 새 행을 만든다. 이전 라벨·규칙·**이유**가 `label_history` 에 남는다(이유가 비어 있으면 거부).
3. 평가셋 파일의 버전(첫 줄 주석)을 올리고, 변경 이유를 같은 주석에 적고, **이전 평가 결과는 지우지 않고 보관**한다(`evals/reports/history/`). 분모가 바뀌므로 바뀐 판본 사이의 숫자를 같은 행으로 직접 비교하지 않는다.
4. 최종 확인용(holdout)은 이 절차로 **개발 중 결과를 보고 고치지 않는다**. 고쳐야 한다면 고친 사실과 이유를 문서에 남기고 그 이후 값은 '최종 확인용'으로 부르지 않는다.

## 10. 알려진 한계

- 독립 라벨러가 없다. 일치도·조정·검증용 정확도는 구현과 합성 예시로만 검증했다.
- 합성 예시 28건의 일치도(kappa 약 0.62, 95% 신뢰구간 약 0.36~0.84, 일치율 75%)는 **내가 일부러 갈리게 만든 데이터의 값**이다. 실제 라벨러의 합의 수준에 대해 아무것도 말해 주지 않는다.
- 우선순위 가중치·업종 위험도·SLA·점유 만료·`too_fast`·기준값(0.60·80%·30건)은 모두 가정한 값이며 실제 운영 데이터로 보정하지 않았다.
- '코드와 모델이 다른 결론'은 보고서에 모델이 처음 말한 판정이 따로 저장되지 않아 '코드만의 판정 ≠ 합쳐진 판정'으로 근사한다.
- 개인 대기열은 같은 브라우저 프로필에 자동 저장되며, 공용 프로필의 다른 사용자가 접근할 수 있다. 사이트 데이터 삭제·기기 분실에 대비한 전체 JSONL 백업이 필요하다. 서버 공동 검수는 접근키·역할·배정·행 잠금·동일 요청 재시도를 구현했지만, 단일 JSONB 행을 직렬 처리하는 소규모 구조다. 전체 앱 SSO/API 인증·대규모 큐·알림 전송·실제 사람 신원 확인은 없다. 실제 운영 DB 연결은 최종 사용자 승인 대기다.
- 업종 분류기(`ops.prelabel.classify_category`)는 키워드 규칙이며 정확도는 `python -m ops.prelabel --eval` 로 재현한다. 데이터셋의 `category` 칸에는 조건·숫자 검사를 위한 자리표시 값이 섞여 있어(예: 금리 문구가 `ecommerce`), 그 칸을 정답으로 한 정확도는 실제 광고주 데이터의 정확도가 아니다.

## 11. 별도 소재 선호의 사람 검토 준비

정책 판정 라벨과 문구의 선호는 별도 과제다. 위 `APPROVE/REVISE/REJECT` 가이드라인을 문구 우열의 정답으로 사용하지 않는다. 2026-10-21에 준비한 [검토자 ZIP](human-review/quality-20261021/reviewer-packet.zip)은 기존 최종 확인용 28쌍의 문구·상품 사실과 **빈 선택·확신·이유 칸**을 담는다. 사례 순서·좌우 위치를 바꾸고 원래 사례 ID·작성자 선호·규칙 점수·모델 답을 검토자 자료에서 제외했다. 선택지는 `left/right/tie/abstain`이며 근거가 부족하면 보류할 수 있다.

`evals/quality_human_review.py`가 원문·자료 해시·사례 매핑·빠진 답을 확인해 별도 제출 파일로 보관한다. 미작성 칸을 무승부나 사람 라벨로 채우지 않는다. **실제 제출은 0건**이며 사람 직접 작성·독립 검토·기존 답 미열람의 확인 진술도 신원·독립성을 자동 검증하지는 않는다. 기존 평가 라벨과 실제 모델 원본에 합쳐 넣지 않는다.

모델 측의 새 정성 계약은 네 기준의 양쪽 원문 인용·관련 사실·중요도를 요구하고 두 순서의 선택·근거가 다르면 보류한다. [2026-10-21 실제 실행 원본](../evals/reports/live_features/features-20261021-run1.json)에서 **채택 16/28, 보류 12/28, 채택하며 작성자 선호와도 일치 13/28**이었다. 보류 사유는 순서에 따라 선택이 바뀐 2개, 인용·근거 검사 실패 7개, 중요한 기준의 불일치 3개다. 근거 검사 전의 두 순서·작성자 선호 일치는 **18/28**로 별도 기록한다. 새 프롬프트·근거 계약을 사용했으므로 이전 실행의 **21/28**과 단순 정확도 증감으로 비교하지 않는다. 이는 출처와 내부 일관성의 검사이며 실제 사람의 선호나 광고 성과를 대신하지 않는다. 빈 사람 검토 자료를 배포할 준비가 됐다는 사실과 실제 제출 **0건**을 구분한다.
