# 공동 검수 저장소 독립 검토 · 2026-10-21

## 검토 범위와 현재 결과

검토 대상은 `ops/team_review.py`의 서버 명령 경계, `ops/team_review_store.py`의 PostgreSQL 저장 경계, 그리고 이 오류를 받는 `ui/team_review_view.py`의 재시도 처리다. 최초 검토에서는 운영 코드를 수정하지 않고 `tests/test_team_review_adversarial.py`에 재현 사례를 추가했다. 재현을 확인한 뒤 주 구현 담당자가 운영 코드를 수정했다. 이후 전체 집계로 앞선 판정을 추론할 수 있는 응답 경계를 닫도록 승인받아 검토자가 `overview` 분기만 추가 수정했다.

최종 로컬 실행은 코어·독립 경계·UI 관련 테스트 세 파일에서 **62개 통과, 실제 PostgreSQL이 필요한 3개 건너뜀**이다. 이 중 독립 경계 파일의 통과 사례는 30개다. 로컬 환경에서는 PostgreSQL 연결을 사용할 수 없었다. 따라서 아래의 실제 커밋·동시성 테스트를 로컬 통과 항목으로 세지 않는다. CI는 `PREFLIGHT_TEAM_TEST_DATABASE_URL`로 별도 PostgreSQL 서비스를 제공해야 한다.

```sh
.venv311/bin/python -m pytest tests/test_team_review.py tests/test_team_review_adversarial.py tests/test_team_review_ui.py -o addopts='' -q --tb=short
```

관측 결과: `62 passed, 3 skipped in 3.43s`. 원본 인사이트 평가 데이터와 기존 보고서는 이 후속 검토에서 수정하지 않았다. 테스트용 키는 출력하지 않았고, 예외나 테스트 객체 표현에 키가 노출되지 않도록 가렸다. DB 연결 주소도 출력하지 않았다.

## 재현한 문제와 수정 확인

| 문제 | 재현한 동작 | 수정 후 확인한 동작 |
|---|---|---|
| 작업 기록 한도가 권한 회수까지 막음 | 검수자가 빈 배정 요청으로 마지막 영수증 자리를 채우면 관리자의 접근 중단·키 교체도 `CapacityReached`로 거절됨 | 관리자에게 허용된 두 보안 작업은 일반 작업 기록 한도에 도달한 뒤에도 실행됨. 이전 키는 사용할 수 없음 |
| 저장 크기 한도가 권한 회수까지 막음 | 현재 상태 크기까지 한도를 낮추면 보안 작업의 영수증 증가분 때문에 작업이 거절됨 | 보안 작업은 일반 저장 크기 입장 제한을 넘겨도 실행됨 |
| 보안 작업 이후 관리 화면을 다시 열 수 없음 | 보안 작업으로 상태가 일반 한도를 넘은 뒤 `overview`·`accounts`가 크기 검사에 걸림. UI가 이 두 조회를 먼저 요구하므로 추가 권한 회수를 할 수 없음 | 읽기 요청에는 일반 작업의 저장 크기 입장 제한을 적용하지 않음. 관리 화면을 다시 열 수 있음 |
| 만료 집계가 같은 요청의 저장 결과와 다름 | 만료된 배정에 대해 먼저 집계를 만들고 뒤에서 회수함. 응답은 배정 1건, 본인 배정은 0건, 저장본은 대기 1건으로 서로 달랐음 | 모든 명령 처리 전에 만료 배정을 회수해 응답과 저장본이 같은 시점의 상태를 반영함 |
| 잘못된 입력을 저장 결과 미확인으로 처리함 | 리스트인 작업 이름·계정 ID·역할, 리스트인 이름·업종, `null`·정수인 근거 목록, 정수인 랜딩 내용, 리스트인 반납 항목 ID가 `TypeError`로 빠짐. 예약된 담당자 이름은 일반 `ValueError`로 빠짐 | 요청 이름·계정 ID와 바깥 입력 필드의 타입을 검사하고 이름 검증 오류를 `InvalidCommand`로 전달함. 원본 상태를 바꾸지 않고 입력 수정을 허용함 |
| 저장 어댑터가 잘못된 입력을 정상 작업으로 바꿈 | `payload or {}`가 `[]`, `""`, `0`, `False`를 빈 객체로 바꿔 배정 명령을 실행할 수 있었음 | `None`만 생략된 입력으로 취급함. 네 잘못된 입력은 쓰기 전에 `InvalidCommand`로 거절됨 |
| 전체 집계로 앞선 검수자의 판정을 추론함 | 한 광고에 두 번째 판정을 제출한 사람이 `overview`의 완료·의견 갈림 수를 보고 앞선 판정과의 일치 여부를 추론할 수 있었음 | 전체 `stats`는 관리자에게만 반환함. 검수자·조정자는 계정 정보·본인 배정·필요한 검수 수와 공통 응답 버전만 받음 |

첫 재현 묶음은 10개 중 **8개 실패, 2개 통과**였다. 첫 수정 뒤 추가한 관리 화면·입력 검사 묶음은 20개 중 **새 10개 실패, 기존 10개 통과**였다. 저장 어댑터 경계와 추가 보호 동작까지 확인한 중간 결과는 **25개 통과, DB 3개 건너뜀**이었다. 마지막 집계 공개 범위 변경도 테스트를 먼저 작성했고 **5개 실패, 25개 통과, DB 3개 건너뜀**을 확인한 후 수정했다. 최종 로컬 실행에서는 독립 경계 파일의 30개 사례가 모두 통과했다.

집계 공개 범위 회귀는 판정 일치·의견 갈림 두 상태와 검수자·조정자 두 역할을 조합한다. 비관리자 응답에는 `account`, `held_items`, `required_labels`, 공통 명령 메타데이터인 `revision`만 있는지 확인하고, 관리자 응답에는 두 상태의 정확한 집계가 남는지 확인한다. 만료 회귀는 검수자의 본인 배정 해제와 관리자의 동일 시점 집계를 각각 검사한다. UI는 원래 관리자 경로에서만 `stats`를 사용하므로 수정하지 않았다.

## 함께 확인한 보호 동작

- 키를 교체해도 계정의 고유 ID를 바꾸지 않는다. 관리자가 본인 키를 교체한 요청은 새 키로 같은 요청 ID를 보내도 같은 영수증을 받는다. 이전 키는 사용할 수 없다.
- 인증은 영수증 조회보다 먼저 수행한다. 만료된 키는 과거에 성공한 배정 요청을 다시 보내도 결과를 받을 수 없다.
- 계정을 비활성화하면 그 계정이 잡고 있던 배정만 즉시 반납한다. 같은 광고를 잡은 다른 검수자의 배정은 보존하고 새 검수자에게 빈 자리를 줄 수 있다.
- 계정 ID, 역할, 판정 작성자, 조정 작성자를 호출자가 자유롭게 대체할 수 없다. 판정·조정 기록에는 인증된 계정 ID를 서버가 넣는다. 키 교체만으로 같은 계정이 같은 광고를 두 번 검수하는 길을 만들지 않는다.
- 검수자에게 보내는 광고 사본에는 다른 검수자의 판정·이유·사전 판정·정답·원본 출처 ID를 포함하지 않는다. 조정할 판정은 조정자 역할에만 제공한다. 화면의 검수자 경로는 전체 계정·내보내기·조정 조회를 사용하지 않는다.
- 내보내기는 서로 다른 계정의 기록을 실제 참여자 확인이나 독립 검수 증거로 바꾸지 않는다. `identity_verified=false`, `independence_verified=false`를 명시하고 합성 예시는 기본적으로 제외한다.
- `_fields`를 호출하는 모든 허용 필드 집합을 타입 표와 대조했다. 허용 필드 19개와 타입 규칙 19개가 일치하며 빠진 항목은 없다. 광고·근거·판정의 내부 구조는 기존 Pydantic 모델이 추가 검증한다.

UI의 확정 거절 목록은 `TeamReviewError`, `ValidationError`, `QueueError`, `AnnotationRejected`다. 이 경우 미확인 요청을 지우고 입력을 고칠 수 있다. 저장 여부가 확인되지 않은 전송 오류는 요청 ID와 입력을 보존해 같은 요청으로 확인한다. 서버의 입력 오류를 일반 `Exception`으로 남겨 두면 두 번째 경로에 들어가기 때문에 위 타입 검사는 화면 동작에도 필요하다.

## 실제 PostgreSQL에서 실행하도록 준비한 검증

아래 세 사례는 단위 테스트의 가짜 연결로 트랜잭션을 흉내 내지 않는다. 별도 테스트 스키마를 만들고 실제 PostgreSQL에 쓴 뒤 다른 연결로 상태를 확인한다. 테스트가 끝나면 해당 테스트가 만든 무작위 이름의 스키마만 제거한다.

| 사례 | 장애·동시 실행 조건 | 기대 결과 |
|---|---|---|
| 커밋 전 실패 | 실제 `UPDATE`가 실행된 뒤, 트랜잭션을 커밋하기 전에 예외를 주입 | 배정과 영수증이 모두 롤백됨. 같은 요청 ID로 재시도하면 한 광고만 배정됨 |
| 커밋 후 응답 유실 | 실제 연결의 커밋이 완료된 직후 응답 유실을 나타내는 예외를 주입 | 다른 연결에서 배정과 영수증을 모두 확인함. 같은 요청 ID로 재시도해도 두 번째 광고를 배정하지 않음 |
| 검수자의 동시 배정·제출 | 한 광고에 검수자 3명이 동시에 배정을 요청하고, 배정된 두 검수자가 동시에 판정을 제출 | 필요한 검수자 두 명만 배정됨. 두 계정의 판정이 모두 남고 배정이 비워지며, 같은 판정이면 완료 상태가 됨 |

연결 실패는 실제 네트워크를 끊는 대신 실제 트랜잭션의 전후에 예외를 주입한다. 검증 대상은 저장 어댑터의 롤백·커밋·영수증 재시도 경계다. 장기간의 네트워크 장애나 데이터베이스 장애 복구를 검증했다는 뜻은 아니다.

## 운영 범위와 남은 사항

일반 한도는 광고 2,000건, 계정 100개, 작업 영수증 10,000개, 저장 상태 30MB, 명령 입력 1MB다. **작업 영수증 수와 저장 상태 크기는 일반 작업을 새로 받는 한도**다. 읽기와 관리자 보안 작업을 막는 절대 상한으로 해석하면 안 된다. 보안 작업 영수증은 그대로 남기므로 관리자가 계속 키를 교체하거나 접근 상태를 바꾸면 일반 저장 한도를 넘을 수 있다. 일반 작업 한도에 도달한 공간의 보존·이관 절차는 별도 운영 과제다.

한 공간의 상태를 하나의 JSONB 행으로 저장하고 행 잠금 아래에서 명령을 처리한다. 이 검토는 작은 팀 공간의 상태 보존과 권한 경계를 다룬다. 대규모 처리량, 읽기 병렬화, 장기간 저장 증가, 여러 조직을 나누는 기능을 검증한 결과가 아니다.

관리자 키는 90일 뒤, 일반 담당자 키는 30일 뒤 만료된다. UI의 담당자 키 재발급 대상에는 관리자 본인이 포함되지 않는다. 서버 명령은 관리자 본인 키 교체를 지원하지만, 만료 전 교체 및 이미 만료되거나 분실한 관리자 키의 복구는 서버 운영 절차가 필요하다. 초기화가 기존 저장 공간을 덮어쓰거나 폐기된 키를 되살려서는 안 된다.

검수자·조정자 `overview`에서 집계를 제외한 것은 해당 응답으로 앞선 판정을 추론하는 경계를 닫은 것이다. 조정자는 별도 권한이 있는 `disagreements` 명령으로 조정할 광고의 판정을 볼 수 있다. 어느 역할의 키가 실제로 서로 다른 참여자에게만 전달됐는지까지 확인하는 기능은 아니며, 실제 독립 참여자 확인과 혼동하지 않는다.
