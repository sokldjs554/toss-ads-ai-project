# 공고의 네 업무를 모두 채운 기능 — 무엇을 하고, 무엇을 재었고, 무엇을 못 하는가

토스 Ads **AI Engineer (Ads)** 공고의 업무는 ① 대화형 캠페인 셋업 ② AI 광고 심사 자동화 ③ 성과 리포트 인사이트 ④ AI 광고 소재 자동 생성입니다. 처음 버전은 ②를 중심으로 ①④의 한 번짜리 버전만 있었고 ③은 없었습니다. 이 문서는 그 빈칸을 채운 기능들을 한곳에 설명합니다.

**읽기 전에.** 아래 숫자는 모두 **이 프로젝트가 만든 합성 데이터·사례**에서 잰 값입니다. 라벨과 기대값은 규칙을 쓴 같은 사람이 달았고 독립 검증은 없습니다. 각 표의 **개발용**은 로직을 만들며 본 데이터라 점수가 높게 나오고, **최종 확인용**은 로직을 고정한 뒤에 만들어 결과를 보고 고치지 않았습니다(나쁜 결과는 나쁜 그대로 적습니다). 실제 AI 모델의 능력이나 실제 광고 데이터의 정확도가 아닙니다. 표의 숫자는 `evals/reports/` 의 저장된 결과에서 생성되며 `tests/test_feature_docs.py` 가 어긋남을 잡습니다. 화면에서는 ‘품질 확인 › 새 기능 평가’ 에서 같은 표를 봅니다.

실제 AI 모델로 이 새 기능들을 잰 것은 **하나도 없습니다**(키가 없는 환경에서 구현하고, 모델 경로는 가짜 제공자로 검증 로직만 시험했습니다). 모델이 하는 일은 모두 ‘제안’이고, 코드가 원문·입력과 대조해 통과한 것만 씁니다.

## 1. 대화형 캠페인 셋업 (여러 턴)

**하는 일.** 광고주가 말로 목표·예산·타겟을 알려 주면, 11개 항목(상품·업종·목표·월 예산·타겟·기간·랜딩 주소·꼭 넣을 조건·말투·세트 수·입찰 방식)으로 이해하고, 모자란 것만 한 번에 최대 2개씩 되묻습니다. 이미 말한 것은 다시 묻지 않고, “예산을 150만원으로 줄여줘” 같은 **수정 요청**과 앞뒤가 안 맞는 **모순**을 구분합니다. 필요한 정보가 모이면 기존 플래너로 캠페인 구성을 만들어 미리 보여 주고, 이후 수정은 바뀐 부분을 비교해 보여 줍니다. 완성된 내용은 ‘이 내용으로 광고 작업 채우기’ 로 기존 입력 칸에 들어가 기존 심사 흐름으로 이어집니다.

**코드와 모델의 역할.** 키가 없으면(그리고 브라우저 실행판에서는) **정해진 규칙**(`agents/conversation_rules.py`)이 한국어 말을 읽습니다. 키가 있고 사용자가 비용을 확인하면 모델(`Task.CONVERSE`)이 값을 제안하고, 코드가 **근거 구절이 사용자의 말에 글자 그대로 있는지·숫자가 같은지·허용된 값인지**를 대조해 통과한 것만 씁니다. 규칙의 값과 모델의 값이 다르면 규칙이 이기고 되묻습니다. 모델이 의미로 옮긴 업종·목표와 사용자가 확인하지 않은 조건은 사용자가 ‘네’ 하기 전에는 확정되지 않고, 확인하지 않은 조건은 광고에 꼭 들어갈 사실이 되지 않습니다. 모델의 한마디에서 승인·성과 보장이나 없는 숫자가 나오면 정해진 문장으로 바꿉니다. 만 19세 미만 타겟·정책 위반 의도·광고 불가 업종·숨은 지시문은 기존 입력 검사(`guardrails/input_guard`)를 그대로 씁니다. 대화는 12번·한 번에 1,000자까지입니다.

**한계.** 이 숫자는 규칙 기반 이해의 값이고 실제 모델의 이해력이 아닙니다. 대화는 만든 사람이 쓴 가상 대화이고 라벨도 같은 사람이 달았습니다. 플랫폼 제약(만 19세 미만 불가는 기존 값, 세트당 월 최소 30만원, 월 60만원 미만은 세트 1개, 세트 최대 3개, 하루·주 예산의 월 환산)은 **이 프로젝트가 가정한 값**이며 실제 토스 Ads 의 기준이 아닙니다. 캠페인 구성 미리보기는 실제 성과·심사 승인과 무관합니다. CI 의 게이트는 개발용만 막고 최종 확인용은 보고만 합니다(알려진 오염 1건이 있어서).

## 2. 상품 페이지(URL)에서 정보 읽기

**하는 일.** 상품 주소(또는 붙여 넣은 페이지 소스, 예시 페이지)에서 상품 이름·가격·사실 후보(조건·혜택)와 랜딩 문구를 뽑아 **초안**을 만듭니다. 핵심은 “외부 페이지는 믿을 수 없는 입력”이라는 점입니다.

- **가져오기(서버 환경에서만).** 주소를 정규화해(10진·16진·8진·IPv6·IPv4-mapped 표기 포함) 사설·루프백·링크로컬·메타데이터 대역을 막고, 이름 확인 결과가 **하나라도** 막힌 대역이면 거부합니다. DNS 리바인딩을 막으려고 확인한 IP 하나에 직접 연결하고(Host·SNI 는 원래 호스트), 리다이렉트는 3번까지 매번 다시 검사하며, 응답은 8초·1.5MB·HTML 형식·압축 해제 상한을 둡니다. 브라우저 실행판에서는 가져오기 대신 붙여넣기와 예시 페이지만 됩니다.
- **읽기.** 표준 라이브러리 파서로 JSON-LD·OG·본문을 읽고, 스타일·속성·주석·noscript 등으로 **화면에 안 보이는 글은 따로 모아 사실로 쓰지 않으며** 지시문 검사를 돌립니다. SPA 껍데기·로그인 벽·여러 상품·블로그 글은 ‘읽지 못함/모호함’ 으로 두고 억지로 만들지 않습니다.
- **사용자 확인.** 초안의 사실은 모두 ‘확인 전’ 이고, 사용자가 직접 골라 확인한 것만 광고 사실(`Fact`)이 됩니다(코드에서 `Fact` 를 만드는 곳이 확인 함수 하나뿐인 것을 테스트가 확인합니다).

## 3. 이미지 소재 — 배너 시안과 이미지 검사

**하는 일.**

- **배너 시안.** 광고 문구를 글 그대로 배치한 **SVG** 배너 후보 3개(크기·템플릿·색 조합 중)를 만들고, 글자 대비(WCAG 계산)·글자 크기·여백·줄 수·고지 가림을 점수와 이유로 보여 줍니다. 이미지 생성 모델은 쓰지 않습니다. 글이 칸에 안 들어가면 **조용히 자르지 않고** 넘침으로 표시하고, 넘침이나 대비 미달이면 총점에 상한을 겁니다.
- **이미지 검사.** 올린 이미지(PNG·JPEG·GIF·WEBP·SVG)를 안전하게 받아들이고(매직 바이트 판별, 크기·픽셀 상한, 확장자·형식 불일치·다중 형식 거부, SVG의 스크립트·외부 주소·엔티티 폭탄 제거), **이미지 속 글자도 광고 문구와 같은 규칙**(표현 규칙·지시문·상품 정보 대조·고지)으로 검사합니다. 배너 안에 ‘원금 보장’ 을 그림으로 넣으면 문구 검사가 못 보기 때문입니다.
- **모델이 읽는 경우**(`Task.VISION`). 모델이 읽은 글은 **사용자가 적은 글과 대조되기 전에는 통과가 되지 않고**, 선언에 없는 문구가 더 있으면 ‘심사 우회 가능성’ 으로 표시합니다. 읽지 못했거나 호출이 실패하면 **어떤 경우에도 통과가 아니라 담당자 확인**입니다. 모델이 봤다고 한 시각 요소(현금 더미·유명인 얼굴 등)는 코드가 검증할 수 없으므로 게재 불가의 근거가 아니라 참고·담당자 확인 표시로만 나갑니다. SVG 는 모델 없이 글자 요소를 직접 읽습니다.
- **문구+이미지 합치기.** 한쪽이 게재 불가면 게재 불가, 이미지를 읽지 못했으면 최소 담당자 확인, 둘 다 통과일 때만 통과(기존 `decide()` 는 바꾸지 않은 그 위의 합산).

## 6. 검수 대기열과 라벨링 파이프라인

**하는 일.** ‘담당자 확인 필요’ 로 끝난 광고가 요청문만 남기고 사라지던 것을 **대기열 → 사람 라벨 → 일치도 점검 → 평가셋 후보**로 이어지는 고리로 만들었습니다.

- **대기열.** 불확실성 표집으로 우선순위를 매기고(낮은 확신·모델 사이 불일치·고위험 업종·코드와 모델이 다른 결론일수록 높게), 마감(SLA)·점유 만료·동시 점유 상한·같은 사람의 중복 라벨 금지·엄격한 상태 전이를 둡니다. 정답을 아는 **검증용 항목**을 섞어 라벨러의 품질을 재고, 라벨러에게는 구분되지 않게 합니다.
- **라벨.** 판정과 규칙 선택이 맞는지(통과인데 게재 불가 규칙 지정 등은 거부), **인용한 구절이 문구 안에 글자 그대로 있는지** 검사합니다. 사전 라벨(자동 제안)은 사람이 확인하기 전에는 라벨이 되지 않고, 앵커링을 줄이려 기본은 숨깁니다.
- **일치도·조정.** 일치율과 Cohen/Fleiss kappa(신뢰구간·표본 부족 경고 포함), 의견이 갈린 건의 조정, 라벨러별 품질.
- **평가셋.** 확정된 라벨만 새 파일로 내보냅니다(기존 평가셋을 덮어쓰지 않음). 개발용/최종 확인용 분할은 **문구 해시로 안정 배정**해 새 항목이 기존 분할을 바꾸지 않고, 근접 중복으로 분할 사이 누수를 탐지합니다. 저장된 평가 기록에서 **라벨이 틀렸을 수 있는 사례**를 찾습니다(라벨을 고치기 전의 저장 기록에서는 G-069 가 맨 위로 잡힙니다).
- **업종 사전 분류기.** 평가셋의 업종 칸 대비 정확도를 코드가 잽니다: 골든셋 51/55, 최종 확인용 10/12(12건이라 구간이 넓음). 개발용 전체는 0.718로 ‘가장 흔한 업종만 찍는’ 기준선(0.708)과 거의 같고, 조건 검사용 사례의 업종 칸이 자리표시값이라 일부 데이터셋에서는 기준선보다 낮습니다 — 낮은 값을 그대로 적습니다.

**한계.** **독립 라벨러가 없습니다.** 다인 라벨 기능은 구현했고 가상 라벨러 2명의 합성 예시 28건과 시뮬레이션 라벨러로만 검증했습니다. 합성 예시의 kappa 0.62(95% 구간 0.36~0.84)는 일부러 갈리게 만든 데이터의 값이며 실제 합의 수준이 아닙니다. kappa 는 같은 가이드라인을 같게 읽었는지를 보여 줄 뿐 라벨이 옳다는 뜻이 아니고, 두 라벨러가 같은 오답을 내도 일치로 확정됩니다. 검증용 항목의 정답도 작성자의 라벨이며 한 사람이 관리자와 라벨러를 겸하면 블라인드는 이름뿐입니다. 우선순위 가중치·마감·점유 만료·기준값(kappa 0.60, 정확도 80%, 표본 30건)은 이 프로젝트가 가정한 값입니다. 라벨 오류 의심 목록은 다시 볼 후보이지 오류 판정이 아닙니다. 대기열은 세션 단위이고 담당자 지정·권한·알림은 없습니다. 가이드라인은 `docs/LABELING.md`.

## 7. 운영 준비 — 운영 경험이 아니라 운영 장치

이 프로젝트에는 **실제 서비스의 운영 데이터가 없습니다.** 광고주 요청을 받은 적도, 서비스로 배포해 장애를 처리한 적도 없습니다. 그래서 운영 시스템이 가져야 할 장치를 만들고 합성 데이터와 저장된 평가 결과로 동작을 확인했습니다. SLO·임계값·용량 공식·롤아웃 기준은 **제안**입니다.

- **감사 기록**: 항목마다 이전 항목의 해시를 잇는 추가 전용 기록. 중간 수정·삭제·순서 변경을 알아채고, API 키·이메일·전화·주민번호 형태를 저장 전에 가립니다. 끝을 잘라 낸 기록과 처음부터 다시 계산한 기록은 마지막 해시를 따로 보관하거나 키를 쓰지 않으면 알아채지 못합니다(변조 탐지이지 방지가 아닙니다).
- **지표·모니터**: 판정 분포·담당자 확인율·단계별 지연·비용·제공자 실패·실패 모드 빈도. 판정 분포 변화·담당자 확인율 급증·비용 이상·지연 SLO 번 레이트·제공자 실패율·인용 환각 비율 규칙을 두고, **합성 스트림에서 탐지 지연과 오경보율을 재어** `docs/OPERATIONS.md` 3.3절에 적었습니다. 정상 스트림에서도 오경보가 있었습니다(판정 분포 규칙 4/100 스트림).
- **효과 계산기(What-if)**: 측정값(저장된 실제 모델 비교 결과의 담당자 확인율·사례당 비용·시간, 윌슨 신뢰구간)과 가정(하루 검수 건수·검수 시간·시급 — 근거 없는 예시)을 **분리해 표시**하고 낙관·비관 범위를 계산합니다. 모든 결과에 “이 평가 사례와 이 가정에서 계산한 값이며 실제 운영 효과가 아닙니다.” 가 붙습니다. 측정한 담당자 확인율은 교차 확인이 없는 평가 경로의 값이라 실제로는 더 높을 수 있습니다.
- **처리량 측정**(`scripts/loadtest.py`, `evals/reports/loadtest.json`): 모델 호출을 뺀 우리 코드의 처리량과 지연입니다. 서비스 용량이 아닙니다.
- **문서**: `docs/OPERATIONS.md`(SLO 제안·런북·롤아웃·개인정보·비용 통제·검수 용량 계획), `docs/SYSTEM_DESIGN.md`(ML 시스템 설계 — 구현한 것과 설계만 한 것을 절마다 구분). 섀도·카나리·수집기·알림 전송·인증·영속 저장소·다중 지역은 **구현하지 않은 설계**입니다.

코드: `ops/audit.py`, `ops/metrics.py`, `ops/monitors.py`, `ops/impact.py`, `scripts/loadtest.py`, `ui/ops_view.py`

## 이 문서의 숫자를 다시 만드는 법

```bash
python -m evals.dialogs --split all --out evals/reports/dialogs_controlled.json
python -m evals.url_ingest_eval --out evals/reports/url_ingest_eval.json
python -m evals.image_eval --save evals/reports/image_eval.json
python -m evals.quality_signals --out evals/reports/quality_signals.json
python -m evals.insights_eval --out evals/reports/insights_controlled.json
python scripts/gen_feature_docs.py        # 이 문서의 표를 저장된 결과로 갱신
```

모두 모델·네트워크 없이 몇 초 안에 끝납니다. 실패 모드는 `docs/FAILURE_MODES.md`(기능별), 테스트는 기능마다 접두사가 있습니다(`tests/test_conv_*`, `test_urlingest_*`, `test_image_*`, `test_creative_quality_*`, `test_insights_*`, `test_labeling_*`, `test_ops_*`).
