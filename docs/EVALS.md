# 평가

2026-10-23에 새 성과 96개와 정책 24개를 실행 전에 고정하고 평가했다. 성과 후보는 개발 대조에서만 개선되고 새 자료에서 악화되어 채택하지 않았다. 규칙/DEMO의 정책 위험 통과 4/16도 그대로 남겼다. [입력·분모·실행 조건·철회 이유](strengthening-20261023.md), [사람 검수표](../evals/reports/strengthening-20261023/policy-human-review.csv)를 참고한다. 이번 실제 모델 호출은 0회이며, 기존 사람 응답 56개(28쌍×2명)는 AI 정확도가 아니다.

이 문서의 숫자는 `evals/reports/` 의 저장된 리포트에서 다시 계산한 것이다 (손으로 적지 않는다). 과거 결과는 `evals/reports/history/` 에 그대로 두고, 현재 결과와 구분한다. 예외가 하나 있다: 이전 커밋의 코드가 낸 값('수정 전 N/M')은 저장된 리포트가 아니라, 그 커밋을 꺼내 `scripts/check_dataset_at_commit.py` 로 다시 재현한 값이다 (명령은 '숫자·조건 비교 보완' 절).

라벨은 '코드가 내야 할 판정' 이다. **같은 저자가 규칙과 라벨을 썼다.** 독립 라벨러·실제 반려 데이터가 없으므로 수치는 일반화의 증거가 아니라 회귀 감시용이며, holdout 도 사람이 검증한 정답이 아니다.

**데이터 출처** (`evals/datasets/PROVENANCE.json` — 데이터 파일 자체는 바꾸지 않아 해시가 유지된다): 데이터마다 작성자·라벨 근거·사람 재확인 여부·규칙 수정에 쓴 적이 있는지·무엇에서 만들었는지를 적는다. 어느 데이터도 ‘독립된 실제 데이터’ 가 아니다(`independent_real_data: false`). 대조 사례와 우회 변형은 다른 사례를 바꿔 쓴 것이라 서로 독립이 아니다. holdout 은 규칙을 고치는 데 쓰지 않았지만 이번 수정 뒤 결과를 확인했고, 그 결과 H-011 에 코드 지적이 하나 늘었다(아래). `PROVENANCE.json` 은 `redteam_seeds`·`adversarial`·`conditions`·`conditions_extra` 를 포함해 이 표의 모든 데이터 파일을 다룬다.

**2차 재점검 (같은 날, 검사 기준 2026.10.4 유지, 모델 호출 없음)**: 위 보강을 마친 코드(`98a2bfb`)를 다시 한 번 로직 검토자와 숫자·조건 검토자가 공격하게 했다(이것도 우리가 시킨 내부 재점검이며 외부 리뷰가 아니다). 재현이 확인된 것만 고쳤고, 재현되지 않았거나 이 프로젝트가 다루겠다고 선언한 범위(여섯 종류의 조건, 범용 한국어 분석기 아님) 밖인 것은 코드를 늘리지 않고 한계로 남겼다. 고친 것:

- **재사용 키**: 키에 적용 업종·교차 확인 경계 기준·이어받은 근거 사실을 더했다. 화면이 키를 만들 때와 재검사가 검사할 때 같은 업종 계산(`recheck_categories`)을 쓴다. 문구가 비어 있으면 재검사를 시작하지 않는다.

## 지표 (`evals/metrics.py`)

| 화면 이름 | 내부 이름 | 정의 | 왜 보나 |
|---|---|---|---|
| 수정이나 게재 제한이 필요한 광고를 통과시킨 비율 | `unsafe_approve` | 라벨이 REVISE/REJECT 인 사례 중 APPROVE 로 판정한 비율 | 가장 중요한 안전 지표. 관측값이지 보장이 아니다 |
| 문제없는 광고에 수정이나 게재 제한을 요청한 비율 | `false_flag` | 라벨이 APPROVE 인 사례 중 REVISE/REJECT 로 판정한 비율 | 과한 요청은 광고주 이탈 |
| 문제없는 광고를 올바르게 통과시킨 비율 / 담당자 확인으로 넘긴 비율 | `benign_correct_pass` / `benign_human_review` | 라벨 APPROVE 중 APPROVE / HUMAN_REVIEW | 담당자 확인은 오탐이 아니지만 올바른 통과도 아니다 — 둘을 섞지 않는다 |
| 담당자 확인 없이 판단한 비율 | `coverage` | HUMAN_REVIEW 가 아닌 비율 (통과·수정 요청·게재 불가 모두 포함) | '자동 승인율' 이 아니다 |
| 규칙별 정밀도·재현율 | `rules` | finding 의 rule_id 집합 vs 라벨 rule_id 집합 (warn 제외) | 어느 규칙이 과·소탐하는지 |

모든 비율에 분모와 Wilson 95% 구간을 붙인다. 분모가 0 이면 `None` 이고 화면은 '대상 없음' 으로 쓴다. 55건에서는 한 건이 약 2~8%p 를 움직인다 (전체 55건 기준 1.8%p, 문제 있는 광고 42건 기준 2.4%p, 문제없는 광고 13건 기준 7.7%p).

### 평가와 실제 판정이 같은 규칙을 쓴다

판정 규칙은 `agents/adjudicator.py::decide(inputs, τ)` 하나뿐이다. 평가 실행기는 사례마다 판정 **원본 입력**(코드 검사의 block/fix 여부, 모델 판정, 확신, 검증된 인용 유무, 원문에 없는 인용 수, 근거 없는 판정 여부, 교차 확인 불일치, 수정안 재검사 결과)을 `inputs` 로 저장하고, 임계값 곡선은 각 τ 에서 이 함수를 다시 부른다 (`curve_method = replay_decide`). 그래서 같은 입력·같은 모델 응답·같은 τ 면 서비스와 평가의 판정이 같다.

원본 입력을 저장하기 전의 리포트(1~4차)는 `legacy_confidence_filter` 로 표시되며, 그 곡선은 "확신 < τ 인 판정을 일괄 담당자 확인으로 간주" 한 것이라 실제 판정과 다를 수 있다. 4차 결과 τ=0.80 에서 실제 자동 판단 52/55 vs 곡선 51/55 가 그 예다 (G-021: 코드가 게재 불가로 확정, 확신 0.6).

**평가 경로의 범위**: 코드 검사 → 1차 검토 모델 → 수정안 재검사 → 판정. 다른 모델 계열의 교차 확인과 가상 사용자 반응은 포함하지 않는다 (리포트의 `scope`). Studio 에서는 확신이 τ+0.1 미만이거나 참고 사항이 있을 때 교차 확인을 한 번 더 부르므로, τ 를 바꾸면 **호출 여부 자체**가 달라질 수 있다 — 그 범위는 저장 응답 재생으로 덮지 못하며 실제 재실행이 필요하다.

**추천 임계값의 유효 범위**: 리포트에 제공자·모델·프롬프트 버전·검사 기준 버전·데이터셋 해시가 기록되고, 화면은 현재 설정과 전부 같을 때만 추천값을 기본값으로 쓴다. 하나라도 다르면 "이 설정의 검증된 추천값 없음" 으로 표시하고 설정값(0.80)을 쓴다 (`evals/runner.py::recommendation_for`).

## 실행


## 방식 비교 — 코드 검사만 · 검토 모델만 · 합친 방식 (`evals/compare.py`)

```bash
python -m evals.compare --estimate                 # 호출 수와 비용 추정(낮게·중간·높게)·상한 경고만 계산 (호출 없음)
python -m evals.compare --out compare_controlled.json   # 키가 없으면 대역(통제된 응답)으로 — 하네스 검증용
python -m evals.compare --cost-cap 3.5 --out compare_live.json   # 키가 있으면 실제 모델 (승인된 범위에서만). 완료되지 못하면 compare_live_incomplete.json
```

결과 원본은 `evals/reports/compare_*.json`(사례별 행 전부 포함)이고 화면은 품질 확인 › 방식 비교다. 같은 고정 사례(골든셋 55 · holdout 12 · 대조 4 · 숫자·조건 39 = 110건)를 세 방식으로 판정한다.

| 방식 | 받는 정보 | 코드의 보정 |
|---|---|---|
| 코드 검사만 | 문구·안내 문구, 상품 정보, 랜딩 문구, 코드로 구현된 검사 기준 | 코드 검사 결과가 그대로 판정 (finding 없으면 통과). 실제 서비스는 코드 혼자 통과를 확정하지 않는다 — 그 운영 방식은 위 ‘코드 검사만’ 행 |
| 검토 모델만 | 같은 정보를 프롬프트로 + 같은 규칙 카탈로그 (비교 전용 프롬프트 `compare-1`: ‘코드가 이미 확인했다’ 는 문장을 모두 뺌). 코드 검사 결과는 받지 않음 | **없음** — 모델이 돌려준 판정을 그대로. 확신 기준(τ)을 얹은 파생 판정은 같은 응답으로 따로 계산 |
| 합친 방식 | 위 전부 + 코드 검사 결과를 모델에 줌 (검토 프롬프트 2026.10.4) | 인용 검증·코드 확정 계층 보호·`decide(τ)`·수정안 재검사 (평가 경로: 교차 확인·가상 사용자 없음) |

보고하는 지표: 잘못 통과한 광고 / 올바른 통과 / 불필요한 수정 요청 / 담당자 확인(올바른 통과와 따로) / 모델 호출·시간·비용 / 대표 성공·실패 사례 / 사례 종류별. 호출이 실패한 사례는 통과·담당자 확인이 아닌 ‘실패’ 로 따로 세고 장애가 섞이면 저장하지 않는다(FM-24). 응답을 받지 못한 요청이 있으면 비용은 ‘이상’. ‘전부 담당자 확인’(잘못 통과 0, 올바른 통과도 0)과 ‘전부 통과’ 를 같은 표에 참고로 둔다. 개발용(골든셋·대조·숫자·조건)과 최종 확인용(holdout)을 나눠 낸다.

- 5차의 담당자 확인 1건(S-04, `zero_width`)도 **보이는 글자**를 끼운 같은 종류다. 공격자는 제로폭 문자를 만든다고 의도했지만 실제로는 글자마다 탭과 'C' 를 끼운 문장이 나왔다. 검토 모델이 확신 0.6 으로 반려를 제안했으나 원문에서 검증된 근거가 없어 담당자 확인으로 갔다. 회귀셋에 `ADV-S-04-zero_width` 로 추가됐다 (CI 의 코드 검사만 통과 0건 조건은 그대로 통과). 32건 중 승인 0건은 이 한 번의 측정값이며 보장이 아니다.
- 담당자 확인·수정 필요로 떨어진 변형도 전부 회귀셋에 수확한다(`harvest()` 는 REJECT 가 아닌 모든 결과를 모은다). CI 는 이 셋에서 코드 검사만으로 통과 0건을 요구한다.

## 실제 처리 기록

`traces/sample_partial_*.json` 은 다섯 사례를 gpt-4o 로 돌린 기록(5차 실행본, run 39044437805, 2026-10-17, 검사 기준 2026.10.2 · 프롬프트 2026.10.3)이다. 이전 4차 기록(run 38933253590, 2026-10-16)은 git 기록에 있다. 광고안이 만들어진 네 사례는 호출 11~12회, $0.11~0.14, 29~37초(다섯 기록 합계 $0.50)였고, '광고 불가 업종' 은 요청 단계에서 멈춰 호출 0회였다. 제공자 장애로 기록된 사건은 없다(있으면 기록을 저장하지 않는다 — FM-24).

| 사례 | 광고안 최종 판정 | 수정안 재검사 (코드 / 의미) |
|---|---|---|
| 정상 요청 (`loan_ok`) | 게재 불가 1 · 수정 필요 2 (점검 통과 0) | 3건 모두 통과 → 검증된 수정안 3 |
| 문제 있는 요청 (`malicious`) | 점검 통과 2 · 수정 필요 1 | 1건: 코드는 통과, **의미 재검사에서 걸려 폐기** |
| 숨은 지시문 (`injection`) | 수정 필요 3 | 2건 통과 → 검증 2, 1건: 코드는 통과, **의미 재검사에서 걸려 폐기** |
| 랜딩 불일치 (`commerce_landing`) | 담당자 확인 1 · 수정 필요 2 | 3건 모두 코드 검사에서 걸려 폐기 |
| 광고 불가 업종 (`prohibited`) | 요청 단계에서 중단 | — |

- 수정 제안이 나온 10건 중 5건이 재검사를 통과해 '검증된 수정안' 이 됐고, 5건은 폐기됐다. 폐기된 5건 중 2건은 **코드 검사는 통과했지만 의미 재검사가 걸러낸 것**이다 — 수정안에 코드 검사만 붙였다면 검증된 것처럼 보였을 사례다. 폐기된 수정안은 화면 어디에도 제시되지 않는다.
- '정상 요청' 에서 실제 모델(gpt-4o)이 쓴 광고안 3개 중 점검 통과는 0개였다. 게재 불가로 판정된 '금리 걱정 없는 신용대출' 은 **코드 규칙을 통과했지만** 검토 모델이 검증된 인용과 함께 반려했다(확신 0.90) — 코드와 모델의 역할이 갈린 사례다. 데모의 '공격적 변형' 은 대역(mock)이 일부러 넣는 것이고, 실제 모델 기록의 이 반려는 모델이 스스로 쓴 문구에서 나온 것이다.
- '문제 있는 요청' 은 입력 단계에서 '원금 보장'·'누구나 무조건 승인'·'업계 최저' 가 삭제되고 요청이 고쳐진 채 진행됐다. 만들어진 3개 광고안 중 점검 통과 2개('쉽고 빠른 모바일 대출', '높은 한도, 부담 없는 상환')는 코드 규칙과 검토 모델(확신 0.95)이 통과시킨 것이지 사람이 확인한 것이 아니다. **같은 종류의 안심 표현이 한쪽에서는 모델이 잡고('금리 걱정 없는') 다른 쪽에서는 통과('부담 없는 상환')했다** — 금리·상환 부담이 작아 보이게 하는 일반 표현은 코드 규칙이 없고(일 단위 이자 표시와 리볼빙 맥락에만 있다) 모델 판단에 기대고 있다. 알려진 약점이다.
- '랜딩 불일치' 에서는 3개 중 1개가 **원문에 없는 인용**(검토 모델 finding)으로 담당자 확인에 갔다.
- 같은 모델의 두 번째 의견은 모든 경우 첫 번째와 같았다. 키가 하나라 독립적인 교차 확인이 아니며 화면에도 그렇게 표시된다.
검사 사례 화면은 이 기록을 모델 호출 없이 보여 주고, 지금 코드로 코드 검사를 다시 돌려 기록 당시와 다르면 그 사실을 적는다.

## 새 기능의 평가 (합성 데이터, 모델 호출 없음)

대화형 설정·상품 페이지 읽기·이미지 검사·소재 퀄리티·성과 리포트는 **저자가 만든 합성 데이터**로 잰다. 기능별 설명·숫자·한계는 [`FEATURES.md`](FEATURES.md), 화면은 ‘품질 확인 › 새 기능 평가’. 지켜 온 절차는 같다.

| 평가 | 명령 | 데이터 | 최종 확인용을 고정하는 방법 | CI 게이트 |
|---|---|---|---|---|
| 대화형 설정 | `python -m evals.dialogs --split all` | 대화 66(개발 40 · 최종 확인용 26) | 규칙·대화 로직 파일의 코드 지문을 고정(`HOLDOUT_FROZEN`), 바뀌면 리포트의 `holdout.clean` 이 false | 개발용만 (`--split dev --gate`). 최종 확인용의 알려진 인젝션 오염 1건은 보고만 |
| 상품 페이지 읽기 | `python -m evals.url_ingest_eval` | 합성 페이지 35(21 · 14) | 추출 코드의 sha256 을 `pages/index.json` 에 기록 | 숨은 글 유출 0 · 예외 0 · 개발용 바닥값 |
| 이미지 검사 | `python -m evals.image_eval` | 합성 사례 119(71 · 48) | 로직 파일의 sha256 을 고정한 뒤 최종 확인용 작성 | 문제 있는 이미지 통과 0 · 읽지 못함→통과 0 · 정화 실패 0 |
| 소재 퀄리티 | `python -m evals.quality_signals` | 선호 쌍 84(56 · 28) | 신호 코드·가중치·무승부 기준의 해시를 `PROCEDURE` 에 기록, 바뀌면 테스트 실패 | 우연 수준 이하면 실패(일부러 느슨) |

공통으로 **이 숫자가 의미하지 않는 것**: 실제 AI 모델의 능력, 실제 광고·페이지·이미지·성과 데이터에서의 정확도, 실제 클릭률·전환과의 관계. 개발용 점수는 로직을 만들며 본 데이터라 낙관적이다. 최종 확인용에서 나쁜 결과가 나온 것(성과 리포트의 오경보 2/4, 상품 페이지의 바꿔 쓴 지시문 유출 2/2, 대화형의 인젝션 오염 1/2 등)은 고치지 않고 그대로 남겼다 — 알려진 구멍은 `tests/test_conv_known_gaps.py` 처럼 strict xfail 로 두어 고치면 알려 준다.

기능별 실패 방식은 `docs/FAILURE_MODES.md`(기능별 묶음)에 탐지·방어·테스트와 함께 있고, 운영 쪽 측정(모니터 탐지 지연·오경보, 처리량, 효과 계산)은 `docs/OPERATIONS.md` 에 있다.

## 한계

- 라벨 저자 = 규칙 저자. 독립 라벨러·실제 반려 데이터가 없다. holdout 도 같은 저자가 썼다.
- 표본이 작다 (골든셋 55, holdout 12). 한 건이 수 %p 를 움직인다.
- 예시 실행 수치는 대역이 낸 것이라 모델 성능이 아니다. 실제 모델 수치는 OpenAI 한 계열만의 결과라 교차 확인의 독립성이 없다.
- 프롬프트·규칙을 고친 뒤 같은 골든셋으로 재측정한 수치는 holdout 이 아니다. 첫 측정(1차) 수치를 그대로 남긴다.
- **검사 기준 2026.10.4·프롬프트 2026.10.4(2026-10-18 보완)의 실제 모델 측정은 방식 비교 한 번(110건 × 세 방식, 위)뿐이다.** 평가 기준선·확신 곡선·임계값 추천·우회 표현 검사·처리 기록의 실제 모델 값은 그 이전 기준(5차까지)의 것이고 옛 기록 그대로 두었다 — 지금 코드의 성능으로 읽으면 안 된다.
- 5차(검사 기준 2026.10.2 · 프롬프트 2026.10.3 · 골든셋 v1.2)의 유효한 실제 모델 결과는 한 번(run 39042649138)뿐이다. 같은 날 먼저 돌린 첫 시도(run 39041334234)만 제공자 장애로 무효였고 `history/*_run5_degraded.json` 에만 있다. 같은 설정을 반복 측정하지 않아 회차 간 흔들림은 아직 알 수 없다.
- 영상 소재는 범위 밖이다. 이미지는 SVG 배너 시안과 이미지 속 글자 검사까지이고(실제 비전 모델의 정확도는 재지 않았다), 상품 페이지는 서버 환경에서만 가져오며 자바스크립트로 그려지는 본문은 읽지 못한다. 새 기능의 평가는 모두 합성 데이터이고 실제 모델로 재지 않았다(위 절).
- 어휘 규칙은 보이는 잡음 삽입('누b구나')을 못 잡는다.
