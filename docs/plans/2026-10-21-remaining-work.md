# 남은 작업 실행 계획 (2026-10-21)

사용자 요청: 아직 끝내지 못한 항목을 이어서 구현·검증·배포한다. 기존 GitHub Secrets를 통한 유료 API 평가 사용 허가는 유지된다.

## 결과 계약

1. 대화: 확인되지 않은 최소 연령은 사용자에게 묻고, 확인한 상한·하한을 모든 광고 세트에 보존한다. 소액 예산 안내를 없애 평가 점수를 맞추지 않는다.
2. 문구 비교: 순서를 바꾼 두 평가와 원문 인용을 보존한다. 근거가 없거나 평가가 다르면 판단을 보류한다. 독립 사람 평가용 자료와 검증 도구를 제공하되 사람 결과를 만들어 내지 않는다.
3. 성과 탐지: 관측된 전환 기간의 데이터를 활용하면서 추세·기준선 불확실성·추가 탐색을 보정한다. 약한 신호를 해결했다고 단정하지 않는다.
4. 공동 검수: 기존 ReviewQueue의 규칙을 서버 트랜잭션 안에서 실행한다. PostgreSQL에 저장하고 담당자별 접근키와 역할을 매 작업마다 검사한다. 키는 해시로만 저장하며, 검수자에게 다른 판정·정답·전체 저장본을 전달하지 않는다.
5. 검증·배포: Python 3.11, 실제 PostgreSQL 동시 요청, 기존 회귀 검사, 새로 제한한 실제 API 실행, 공개 화면과 Render 배포를 확인하고 증거를 기록한다.

## 공동 검수 설계

- 기존 브라우저의 개인 대기열은 유지한다. 공동 작업은 Render 서버 화면에서 이용한다. 브라우저에 DB 주소나 관리 키를 싣지 않는다.
- 한 프로젝트의 검수 공간을 운영한다. 일반 회원 가입·SSO·조직 관리까지 확대하지 않는다. 관리자가 담당자 계정을 만들고 개별 무작위 접근키를 발급한다. 계정의 고유 ID는 키 재발급에도 유지한다.
- 관리자: 광고 추가, 담당자 발급·비활성화, 결과 내보내기. 검수자: 자신이 배정받은 광고만 확인·제출. 조정자: 판정이 갈린 광고의 최종 판단. 계정은 사람의 독립성을 증명하지 않는다.
- DB의 단일 상태 행을 잠근 트랜잭션에서 인증·역할 검사·기존 큐 상태 변경·요청 ID 기록을 함께 커밋한다. 같은 요청 ID와 내용은 기존 결과를 반환하고, 내용이 다르면 거부한다. DB 장애 시 로컬 저장으로 바꾸지 않는다.
- 전체 상태를 서버가 읽는 방식은 소규모 검수 공간의 선택이다. 항목·계정·저장 크기에 한도를 두고, 대규모 처리량을 주장하지 않는다. 향후 항목별 행/잠금으로 나누는 경계를 문서화한다.
- 새 자원은 무료 요금제 범위의 전용 DB만 사용한다. 실제 광고주 데이터·실제 사람 라벨·실제 운영 성과는 코드로 대체하지 않는다.
