# 실제 수정안 분기의 보조평가 — 2026-10-21

## 측정이 필요한 이유

기존 `features-20261020-run1/2/3.json`의 파이프라인 광고는 실행마다 8개, 총 24개다. 모든 행의 `rewrite_status`가 `none`이었다. 그 결과로 원문 검토·근거 검사·최종 판정 경로의 동작은 볼 수 있지만, **위반 원문에서 실제 모델이 수정안을 만들고 그 수정안을 같은 정책으로 다시 검토하는 분기가 성공했는지**는 알 수 없다. 원문이 통과해서 수정 분기를 실행하지 않은 경우를 수정 성공으로 세지 않아야 한다.

`evals/live_rewrite.py`는 기존 생산 함수 `agents.recheck.recheck`를 직접 호출하는 별도 보조평가다. 대체 프롬프트나 평가 전용으로 느슨한 검사를 만들지 않았다. 기존 다섯 기능의 입력·점수·분모와 원본 보고서는 바꾸지 않으며, 결과는 `supplemental_results`와 `supplemental_summaries`에 따로 기록한다.

## 사전에 정한 입력

파일은 `evals/datasets/rewrite_regression_20261021.json`이다. 가상의 상품과 공개 합성 광고 4개이며 AI 작성 자료임을 파일에 명시했다. 실제 광고주 데이터, 실제 사람의 라벨, 모범 수정 문구는 들어 있지 않다. 실측 후 유리한 사례만 고르거나 원문을 바꾸지 않도록 실행 요청에서 파일 해시를 고정한다.

SHA-256: `7d272ed279868c2c5b6418732306a6f8735995d2258ab07730fc49a356eb5301`

| 사례 | 고정한 위반 원문 | 실제 모델 호출 전 코드 판정 | 검출한 규칙 |
|---|---|---|---|
| RW01 | 근거 없이 “타사보다 좋은” 머그컵 | REJECT | TA-COMPARE-01 |
| RW02 | 기간 근거 없는 “오늘만” 영어 강의, 교육 고지 누락 | REVISE | TA-URGENCY-01, FIN-DISCLOSE-EDU-01 |
| RW03 | 최소 구매액·기한·1인 1회 조건 없는 할인 쿠폰 | REVISE | GRND-COND-01 |
| RW04 | 상품 사실은 18만원인데 9만원이라고 광고 | REVISE | GRND-NUM-01, GRND-CLAIM-01 |

이 코드 판정은 저장소의 현재 정책 카탈로그를 사용한 오프라인 관찰이다. 법률 판단이나 실제 모델의 응답 결과를 뜻하지 않는다. `load_cases`는 호출 전에 모든 원문을 다시 검사하며 예정한 필수 위반이 없거나 원문이 APPROVE이면 거절한다. 추가로 발견한 위반도 결과에 남긴다. 특히 RW02는 긴급성 표현만 없애서는 충분하지 않으며 같은 교육 고지도 충족해야 한다.

## 실행 경로와 성공 조건

원문과 상품 사실을 생산 `recheck` 함수에 전달한다. 이 함수는 코드 검사, 실제 모델의 원문 검토와 `proposed_rewrite`, 기존 `check_rewrite`, 동일 카탈로그·조건의 최종 판정을 수행한다. `enable_second_opinion=True`를 유지하며 추가 검토가 필요하면 기존 라우터를 따른다. 보조평가가 모델 판단을 강제로 수정하거나 정답 문구를 주입하지 않는다.

한 사례의 모든 성공 조건은 다음과 같다.

1. 코드 검사로 원문 위반을 확인했고 원문의 최종 판정도 APPROVE가 아니다.
2. 호출 장부에 원문 검토의 성공한 실제 `review` 호출이 있다.
3. 모델의 `proposed_rewrite`가 존재하며 전체 문구가 원문과 다르다.
4. 호출 장부에 수정안의 성공한 실제 `review` 호출이 있다.
5. 기존 생산 재검사의 `rewrite_status`가 VERIFIED다.
6. 검증된 수정안을 같은 정책으로 다시 코드 검사했을 때 APPROVE다.
7. 위험한 수정안이 검증된 문구로 노출되지 않았고 실패한 단계가 없다.

원문과 수정안 호출은 같은 실행의 장부에서 `task=review`, 정확한 단계 라벨, `status=success`로 확인하고 각각의 `ordinal`을 결과에 보관한다. 원문에서 한 번 호출했다는 이유만으로 수정안 검토까지 실행했다고 보지 않는다. 각 구조화 응답, 제공자·모델·수리·fallback 정보도 `model_observations`에 저장한다. 예외는 타입, 단계, 실패 코드만 저장하고 예외 문자열의 민감 정보를 보고서에 복사하지 않는다.

원문이 우연히 통과하거나 수정안이 없으면 수정 성공이 아니다. 위험한 수정안이 코드 검사에서 먼저 차단되어 실제 의미 재검사를 실행하지 않은 경우에도 `real_rewrite_review=false`로 남는다. 이 경우 차단 동작은 맞지만 실제 모델 재검사 성공으로 셀 수 없다. 재검사 실패나 예산 중단 때는 검증되지 않은 제안을 별도 `proposed_rewrite`로만 기록하며 `verified_rewrite`에 노출하지 않는다.

예산은 기존 `FeatureRun`의 공유 장부가 관리한다. 수정안이 생성된 뒤 재검사 예산이 끝나도 원문 응답·제안·호출 장부를 체크포인트에 보관한 다음 중단한다. 기본 경로의 예상은 사례당 원문/수정안 검토 2회, 총 8회다. 수리·재시도·제공자 전환·추가 의견은 이보다 호출을 늘릴 수 있으므로 이 수가 최대 호출 보장은 아니다. 기존 예산 상한을 늘리는 코드는 추가하지 않았다.

## 실행 요청과 보고서

실측 운영자는 기존 요청에 다음 필드를 추가한다. `input_sha256`에는 기존 입력들의 해시도 계속 포함한다.

```json
{
  "rewrite_fixture_path": "evals/datasets/rewrite_regression_20261021.json",
  "planned_supplemental_cases": {"rewrite": 4},
  "input_sha256": {
    "evals/datasets/rewrite_regression_20261021.json": "7d272ed279868c2c5b6418732306a6f8735995d2258ab07730fc49a356eb5301"
  }
}
```

검증은 fixture 경로의 안전성·해시·예정 개수를 확인한 뒤 실제 호출을 허용한다. 코드와 정책 fingerprint는 기존 실측 요청 동결에 함께 포함한다. `GROUPS`는 여전히 `vision/conversation/insights/quality/pipeline`이며, 새 4개 사례는 원래 파이프라인의 8개 분모에 합치지 않는다.

UI는 보조평가를 별도 표로 표시한다. 예정, 시도, 실제 응답, 모든 단계 통과 수를 구분하며, 원문과 수정안의 실제 호출이 모두 필요하다는 설명을 붙인다. 요청에는 보조평가가 예정돼 있지만 결과가 없다면 보고서 전체를 완료로 표시하지 않는다.

## 검증 증거와 남은 한계

`tests/test_live_rewrite.py`의 12개 검사는 고정 입력의 실제 코드 위반, 네 가지 생산 경로, 원문 APPROVE 시 실패, 위험한 수정안의 조기 차단, 의미 재검사 오류, 호출 전 원문 거부, 다섯 기능과 별도 집계, 예산 중단 시 제안 보존, 요청 해시/예정 개수 필수 조건을 검사한다. 응답 제공자는 명시적인 통제된 테스트 객체이며 실제 네트워크를 호출하지 않는다. 테스트의 성공용 문구는 fixture나 실제 모델 프롬프트에 들어 있지 않다.

품질·사람 검토·runner·UI·장부와 함께 검증한 전체 관련 명령은 `docs/review-quality-remaining-20261021.md`에 있다. **226개 검사 통과, 13.03초, Python 3.11.17**이며 그중 보조평가 검사가 12개다.

이 문서 작성 시점에 새 보조평가의 실제 API 성공률은 아직 측정하지 않았다. 실측 운영자가 동결 요청으로 새 실행을 수행하고 전체 호출 장부를 포함한 새 보고서에서 결과를 확인해야 한다. 네 합성 사례에서의 성공은 실제 광고 전반의 안전성, 광고주 만족도, 최종 법적 적합성을 증명하지 않는다. 같은 정책을 두 번 적용해도 정책 자체가 놓치는 문제나 모델이 일관되게 오해하는 내용은 남을 수 있다.
