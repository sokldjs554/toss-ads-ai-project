# 2026-10-20 별도 작성 holdout: 첫 실행 결과

## 결론과 평가 범위

이 첫 실행은 남은 한계가 모두 해소되었다는 근거가 아니다. 새 대화 20개 중 모든 검사를 통과한 것은 **14개**였고, 성과 시나리오는 탐지 대상 사건 **35개 중 18개(51.43%)**를 찾았다. 명확한 원인 시나리오의 top-1/top-3 정답률은 모두 **18/32(56.25%)**였다. 정상 시나리오 40개에서는 잘못된 알림이 없었지만, 이를 실제 계정에서 정상일 때 잘못 알린 비율 0%로 해석할 수 없다.

이 문서는 `evals/reports/dialogs_holdout_20261020.json`과 `evals/reports/insights_holdout_20261020.json`의 **첫 결과를 그대로 보존하고 해석**한다. 이 평가 이후 데이터, 라벨, 사건 강도, 구현을 수정하지 않았고 실패 사례를 제거하지 않았다. 대화의 세 실패에는 정책 라벨 누락 또는 해석 모호성이 있어, 구현 실패와 구분한다. 점수는 원래 동결 라벨로 계산한 값 그대로다.

대화 실행은 `rules` 추출기와 이를 되풀이하는 demo/mock 제공자를 사용했다. 성과 실행도 합성 데이터, 결정론적 엔진, 템플릿 및 보고서 변형 시험이다. **실제 언어 모델 API 품질, 실제 광고주 대화, 실제 토스애즈 계정 성과를 검증한 결과가 아니다.** 실제 API 평가는 이 문서의 담당 범위 밖이며 별도 결과와 구분해야 한다.

## 사전 동결과 출처

작성자는 구현 담당과 분리된 AI 에이전트 `/root/ads_blind_holdout`이다. 새 데이터를 쓰기 전에 확인한 것은 평가 CLI의 `--help`, 공개 `ScenarioSpec`/`EventSpec` 필드와 API 문서 문자열, 그리고 루트가 제공한 사건 매개변수 및 대화 라벨 계약이다. 엔진 구현, 기존 시나리오 본문, 테스트 본문, 과거 출력 본문은 보지 않았다. 결과를 본 뒤 이 holdout을 활용하는 개발은 이미 본 회귀 데이터에 대한 작업이며, 이후 실행을 새로운 맹검 결과로 부를 수 없다.

## 데이터 구성과 라벨 계약

대화는 새 한국어 문장 **20개 대화, 총 30턴**, 대화당 1–3턴이다. 12개 카테고리와 5개 목표를 포함한다. 일반 예산 표현, 열린 연령 범위, 이모지, 여러 단어로 된 톤, 카테고리 부정과 정정, 일반 예산 충돌, 명시적 예산 변경, 한국어·영어 지시 주입을 다룬다.

필수 카테고리·목표·월 예산이 명시되면 optional 필드가 없어도 준비 완료로 라벨링했다. 말하지 않은 슬롯이나 연령 하한을 임의로 채우지 않았다. 단순히 다른 예산을 다시 말한 경우에는 확인이 필요하며, 충돌 중인 예산 값은 값 정확도 채점에서 제외했다. 명시적 변경은 새 값으로 갱신되어야 한다. 주입은 처음 발견한 공격부터 **같은 턴 끝까지** 격리하고, 앞의 정상 문장은 보존하며, 뒤의 새 정상 턴에서는 회복할 수 있다는 계약을 적용했다. 모델만 추론한 카테고리·목표에는 live 모드에서 별도 확인이 필요할 수 있으므로 demo 라벨을 live 모드에 그대로 적용한 성능 주장에 주의해야 한다.

### 주입 지표의 분모 주의

원본 보고서는 `injection_dialogs: 7`, 오염 `0/7`을 출력했다. 그러나 작성된 공격 대화는 `h26-d17`–`h26-d20`의 **4개**다. 카테고리 부정·정정·예산 변경의 비공격 사례 `h26-d13`, `h26-d14`, `h26-d16`에도 `forbidden` 값 검사를 두었고 이들이 원본 분모에 들어갔다.

### 모호성·저볼륨 결과와 라벨 한계

저볼륨 `h26-p073`–`h26-p075`는 insufficient, `h26-p076`은 partial이었고 추가 데이터 또는 관찰을 제안했다. 차원·보조 신호를 없앤 `h26-p077`–`h26-p079`는 사건을 찾지 못하고 `keep_watching`을 제안했다.

원본의 `ambiguous_not_asserted`는 1.0, `ambiguous_undetermined`는 0.0이다. 이 집계만으로 모든 불확실한 사례에서 명시적으로 “원인을 정하기 어렵다”고 설명했다고 말할 수 없다. **`h26-p080`은 ambiguous=true, detectable=false로 작성했지만 `tracking_break`를 top-1, `supported`로 반환했다.** 이 사례는 짧게 겹친 tracking/landing 사건이며 두 원인을 후보로 기록했다. 짧고 잡음이 큰 사건이 검출 불가능할 것이라는 작성자의 가정은 실제 검출 가능성을 독립적으로 입증한 라벨이 아니다. 이 사건을 사후에 명확 사례로 옮기거나 플래그를 바꾸지 않고, 집계와 개별 출력의 해석 한계로 남긴다.

### 보고서 점검 및 변형 시험

보고서의 점검 문제 1건은 `h26-p041`의 `direction_conflict`다. 정상 내용 잘못 버림 11건도 모두 같은 시나리오에 기록되었다. 두 현상이 같은 시나리오에 있다는 것은 확인했지만, 구현을 열어 원인을 진단하거나 고치지 않았다.

881건은 생성 보고서의 변형 주입 시험이다. 881개의 독립된 사용자 공격이나 실제 LLM 응답을 의미하지 않는다. 원본 보고서 결함 1건과 정상 내용 잘못 버림 11건을 함께 공개해야 방어 성공 숫자가 과장되지 않는다.

## 원본 대화 보고서의 메타데이터 문제

새 데이터셋 경로와 전체 SHA, 현재 코드 SHA는 정확하지만, 대화 평가기의 결과에는 기존 회귀 데이터용 설명이 남아 있다. `dataset.role: seen_regression`, 기존 v2 provenance 경로, 오래된 `holdout.frozen`/`historical_report`, 기존 holdout을 튜닝에 사용했다는 설명, 잘못된 `repro` 출력 파일 경로가 새 보고서에도 들어갔다.

이 문서는 해당 원본 필드를 수정해 깨끗한 것처럼 만들지 않았다. 이 데이터셋의 첫 실행 출처는 **사전 동결 SHA·작성 기록·현재 코드 SHA·실제 실행 명령**으로 확인해야 한다. 이전 corpus에 관한 설명을 이 새 corpus의 작성 이력으로 사용해서는 안 된다. 평가기의 데이터별 provenance 출력을 수정하는 일은 별도 과제다. 성과 보고서에서는 새 지문과 held_out 메타데이터가 일치했다.

## 재현 명령과 보존 상태

두 명령은 첫 실행에서 종료 코드 0으로 완료되고 결과 JSON을 저장했다. `--gate`를 쓰지 않았으므로 **종료 코드 0은 위 성능 수치의 합격을 뜻하지 않는다.**

```bash
.venv311/bin/python -m evals.dialogs --dataset evals/datasets/dialogs_holdout_20261020.jsonl --split holdout --out evals/reports/dialogs_holdout_20261020.json
.venv311/bin/python -m evals.insights_eval --dataset evals/datasets/perf_holdout_20261020.jsonl --split holdout --out evals/reports/insights_holdout_20261020.json
```

위 경로는 첫 실행 기록이다. 후속 개발 후 재실행할 때에는 별도의 결과 경로를 사용해 원본을 보존해야 한다. 이후 같은 입력은 이미 본 회귀 평가이며, 다음 맹검 평가는 수정된 엔진을 다시 동결한 뒤 새로 작성한 데이터가 필요하다.

이 작업에서는 프로덕션 코드 변경, 커밋, 푸시를 수행하지 않았다. 전달 범위는 새 데이터 두 개, 사전 provenance 두 개, 원본 결과 두 개, 이 해석 문서다.
