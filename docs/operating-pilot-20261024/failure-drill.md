# 실패 대응 검증과 오류 기록 누락 수정

기준117d996의 `LiveGateway`는 제공자 오류의 `error_type/http_status/provider_code/provider_param`을 허용된 분류로 생성했지만 `LiveStore.finish_call`은 그 필드를 거부했다. `finally`의 저장 오류가 원래 예외를 덮어써 시간 초과 사유가 일반 실패로 바뀌고 호출 행은 `outcome_unknown`에 머물렀다. 기존 gateway 단위 테스트의 가짜 원장은 저장소 검증을 수행하지 않아 이 연결 결함을 놓쳤다.

새 테스트는 실제 `run_workflow → LiveGateway → LiveStore → PostgreSQL`을 연결하고 외부 SDK 응답만 모의 실패로 대체한다. 시간 초과·스키마HTTP400·일반 오류 세 입력은 수정 전 모두 실패했다. 오류 필드와 제한된 값만 저장소에서 허용한 후 실패 분류·미확인 비용·보류 상태가 저장되고 새 연결로 조회된다. 임의 오류 원문·메시지·부적절한 HTTP값은 거부한다. SDK 원문을 저장하거나 실패를 성공/DEMO로 바꾸지 않는다.

| 확인 범위 | 실행과 근거 | 한계 |
|---|---|---|
| 오류 기록 연결 | 수정 전3실패, 수정 후 해당3통과 | 제공자 실패는 모의 주입 |
| 기존 LIVE 경계 회귀 | 로컬 격리 PostgreSQL에서48통과, 실패·skip0 | 자동 검증이며 사람 사용 아님 |
| 인용·구조·수정 제한 | 기존 engine 테스트의 잘못된 인용·미검사 출력·루프 제한 | 의미적 정책 정확도 평가 아님 |
| 비용·중복·권한·재접속 | 기존 store 테스트의 실제 트랜잭션·동시성·계정 분리 | 로컬 임시 스키마, 운영 장애 유발 아님 |

원본 [red](../evidence/operating-pilot-20261024/failure-red.log)·[green](../evidence/operating-pilot-20261024/failure-green.log)과 JUnit을 보존한다. 초기 테스트 작성에서 일반 실패의 기존 계약을 `provider_failure`로 잘못 예상해 `provider_or_storage_failure`로 바로잡은 후 red를 다시 확인했다. 이 수정은 정책 판정 기대값을 바꾼 것이 아니라 기존 일반 실패 계약을 따른 것이다.

운영 DB에는 읽기 전용 계정·예약 잔액 확인만 수행했다. 과거 실제 실패2건의 사용량·비용은 미확인 상태로 남기며 새 코드로 소급 채워 넣지 않는다. 기존 최종 브라우저와 이번 코드의 검증 결과는 별도 버전으로 기록한다.

## 실제 장애 때 수행할 순서

1. 시각(KST)·요청ID·화면버전·안전한 오류 분류만 기록하고 중복 실행을 멈춘다. API키·원문·원본 SDK 오류를 공개하지 않는다.
2. `내 저장 기록`에서 같은 요청을 조회한다. 결과가 없거나 사용량이 미확인이면 성공·0원으로 추정하지 않는다. 관리자도 기존 호출/감사 행을 덮어쓰지 않는다.
3. 인증·제공자·저장소 상태를 읽기 전용으로 확인하고 원인을 구분한다. 저장소 장애면 복구 후 동일 요청을 먼저 조회하며 새 모델 호출로 복구를 대신하지 않는다.
4. 합성 격리 환경에서 재현·회귀 검증한 수정만 배포한다. 배포 전후 기록·호출 수·감사 내용을 비교하고 대응 시간과 영향 범위를 남긴다.

운영 DB 중단·실제 제공자 장애·장기 자동 감시·복구시간 목표 달성은 이번 훈련에서 입증하지 않았다. 실제 장애와 주입 훈련은 [incident-log.csv](incident-log.csv)의 kind로 분리한다.
