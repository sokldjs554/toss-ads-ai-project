# 추가 유료 평가 독립 검토 · 2026-10-21

## 결과와 범위

예약·재실행·브랜치 변경·분모 누락 경계를 검토해 **11개 실패 사례를 수정 전에 재현**했다. 구현 담당자가 보완한 뒤 독립 검토 파일의 13개 사례를 포함한 **관련 테스트 71개가 통과**했다. 새 manifest의 무료 검증도 통과했다. 이 검토에서는 실제 제공자를 호출하거나 원격 Git 저장소를 변경하지 않았다.

검토 대상은 `.github/workflows/live-remaining.yml`, `scripts/claim_remaining_evaluation.py`, `evals/live_features.py`, `evals/live_rewrite.py`와 비용 장부·실제 재작성·후속 대화 연결이다. 독립 검토자가 추가한 파일은 `tests/test_remaining_evaluation_review.py`와 이 문서다. 운영 코드 수정은 주 구현 담당자가 맡았다.

추가 단계의 전체 예약 상한은 **4달러**, 첫 manifest의 실행 상한은 **2달러·300회**다. 사용자가 승인한 것은 남은 작업과 유료 호출의 계속 진행이며, 4달러와 첫 실행 2달러는 구현자가 정한 제한이다. 첫 예약은 성공·실패·중단 여부와 관계없이 유지한다. 실제 사용량이 적더라도 예약을 반환하거나 재실행에 재사용하지 않는다. 후속 측정이 필요하면 별도 run ID와 새로 고정한 요청으로 남은 예약 범위 안에서 판단한다.

첫 재현 실행은 **5개 실패, 2개 통과**였다. 원본 장부 연결·손상 장부를 보완한 뒤 분모 회귀를 추가했을 때는 **새 6개 실패, 기존 7개 통과**였다. 원래 입력과 결과를 바꾸어 실패를 숨기지 않고 명령·집계 경계를 고쳤다.

## 보존한 입력과 분모

새 요청과 직전 요청을 직접 대조했다.

| 확인 항목 | 관측 결과 |
|---|---|
| 기존 입력 파일 18개의 SHA-256 | 모두 동일 |
| 원래 다섯 그룹의 예정 개수 | 동일: 비전 12, 대화 20, 성과 12, 품질 28, 파이프라인 4 |
| 원래 예정 사례 총수 | 76개 유지 |
| 선택한 성과 사례 ID | 직전 요청과 동일 |
| 별도 보조 사례 | 재작성 4개, 명시적인 연령 답변 후속 대화 1개 |
| 후속 대화의 원래 턴 | 원본 `h26-d04`와 동일하며 뒤에 명시적인 연령 답변을 추가함 |
| 기존 10달러 예약 장부 | 기준 커밋 `4dce790`과 바이트 단위로 동일 |

기존 장부의 SHA-256은 `576c98fb311448fce78456cdac89769c8ecda81a368046ed85763662bcaeb54a`이며 새 manifest의 지문과 일치한다. 원래 76개 결과는 기존 다섯 그룹에 남고, 보조 5개 결과는 별도 배열·요약에 기록된다. 후속 답변의 성공을 원래 20개 대화의 최초 성공률에 합치지 않는다.

새 manifest는 현재 평가 코드·정책·두 예약 스크립트·두 평가 워크플로를 포함한 84개 소스 파일과 원본 18개·보조 2개 입력 파일을 고정한다. 관련 소스나 입력이 바뀌면 다시 지문을 고정해야 하며, 무료 검증을 통과하기 전에는 유료 단계로 진행하지 않는다.

## 재실행과 비용 처리

워크플로는 기존 유료 기능 평가와 같은 동시 실행 그룹을 사용한다. 무료 테스트와 manifest 검증 이후 브랜치를 가져오고, 체크아웃한 `HEAD`와 가져온 `FETCH_HEAD`가 다르면 예약 전에 중단한다. 예약을 커밋하고 원격 브랜치로 정상 push한 다음 별도 단계에서만 제공자 키를 전달한다.

승인하지 않은 브랜치와 이미 움직인 브랜치는 장부를 읽거나 쓰기 전에 거절하는 로컬 회귀가 통과했다. 같은 run ID의 재예약과 누적 4달러 초과는 기존 예약 회귀로 검사한다. 취소된 실행의 예약도 유지한다. 이후 브랜치 이동으로 결과 커밋의 push가 실패할 수 있으므로, 결과는 별도 artifact 보존 단계에도 전달한다. 이 검토에서 GitHub 실행 자체를 발생시킨 것은 아니다.

실제 호출 경로는 `BoundedProvider`의 공유 장부를 사용한다. 각 호출 전에 요청 크기·최대 출력에 따른 금액을 예약하고 checkpoint를 쓴다. 사용량과 모델을 확인한 응답만 토큰 단가로 정산한다. 호출 실패·사용량 누락·모델 불일치는 예약액을 유지한다. 재시도와 다른 제공자로의 전환도 같은 장부를 거치며 SDK 자체 재시도는 0으로 설정한다.

이 장부는 코드에 고정한 단가와 요청 범위에 따른 지출 제어·사용량 기록이다. 제공자의 최종 청구서로 표현하지 않는다. 실행이 강제로 종료돼 개별 호출의 최종 응답을 기록하지 못해도 원격에 사전 저장한 실행 예약 전체를 유지하는 설계다.

## 실제 재작성 경로 검토

보조평가는 원문 위반 네 가지를 무료 단계에서 먼저 확인한다. 원문의 예상 위반 규칙이 실제 코드 검사 결과에 없거나 원문이 이미 통과하면 호출 전에 거절한다.

측정은 생산 `recheck()`를 사용한다. 모델이 원문을 검토하며 제안한 수정안을 같은 정책의 `check_rewrite()`에 전달하고, 필요하면 같은 조건의 추가 검토를 수행한다. 실제 평가 코드는 테스트의 정답 수정문을 주입하지 않는다. 테스트에 있는 통제된 수정문은 임시 테스트 결과에만 사용한다.

성공을 세려면 원문 검토와 수정안 검토 각각의 성공한 실제 호출 ordinal, 원문과 달라진 수정 문구, `VERIFIED` 상태, 수정문의 코드 검사 통과가 모두 필요하다. 따라서 원문에 대한 검토만 성공하거나, 위반 수정문을 코드에서 차단해 의미 검토를 건너뛰거나, 수정안 검토 호출이 실패한 것을 전체 성공으로 세지 않는다.

원문, 제안 수정문, 검증된 수정문, 정책 버전, 판정 기준, 호출 ordinal, 구조화된 모델 관측을 함께 남긴다. 예산 중단 때도 이미 받은 제안과 관측을 보존하고 다음 사례로 진행하지 않는다. 위험한 수정문·수정안 없음·의미 검토 실패·예산 중단에 대한 통제된 회귀가 통과했다. 이 결과는 실제 모델 네 건이 성공했다는 뜻은 아니며, 유료 측정 결과를 받아야 실제 성공 건수를 보고할 수 있다.
