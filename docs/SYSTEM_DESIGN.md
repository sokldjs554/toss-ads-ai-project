# ML 시스템 설계 — 광고 사전 점검 (면접 대비)

"광고가 올라가기 전에 확인이 필요한 구절을 먼저 찾는다"는 이 프로젝트를 *서비스로 만든다면* 어떻게 설계하겠는가를 정리한 문서다.
면접에서 설계를 설명할 때 *이 프로젝트가 실제로 가진 것*과 *말로만 설계한 것*을 섞지 않으려고 절마다 표시했다.

| 표시 | 뜻 |
|---|---|
| **[구현]** | 코드와 테스트가 있다 (파일 경로 표기). |
| **[부분]** | 일부 경로만 구현됐고 나머지는 설계다. 구현 범위와 한계를 절마다 적는다. |
| **[설계만]** | 코드 없음. 필요하다고 판단한 것을 적었을 뿐이다. |

> 이 프로젝트에는 실제 서비스의 운영 데이터가 없다. §2 의 규모는 *가정*이고, 값이 된 숫자는 저장소에서 잰 것(측정)만 그렇다고 적었다.
> 운영 장치(모니터·감사·효과 모델)의 상세와 수치는 [OPERATIONS.md](OPERATIONS.md) 에 있다.

## 1. 문제와 요구사항 [요구 정의 — 구현 여부는 행마다 표시]

**문제:** 광고주가 올린(또는 도구가 생성한) 광고 문구가 플랫폼 정책·금융 광고 규정을 어기는지, 올리기 *전에* 찾는다. 모델은 제안만 하고 코드가 검증·판정한다 — 이것이 설계의 중심 제약이다.

| 구분 | 요구 | 비고 |
|---|---|---|
| 기능 | 문구 검사(표현·필수 고지·근거 없는 숫자·형식·중복·인젝션), 수정안 제시와 재검사, 담당자 확인으로 넘기기, 라벨 수집 | [구현] 검사·재검사, `ops/review_queue.py`의 라벨 고리, `ops/team_review.py`의 서버 공동 검수 |
| 안전 | 확신이 없거나 읽지 못하면 *통과가 아니라 담당자 확인*(fail-closed). 모델 출력(인용·규칙 ID·값)은 코드가 원문과 대조 | [구현] `agents/adjudicator.py`, `guardrails/` |
| 지연 | 대화형 검사는 수 초~수십 초. 일괄 검사는 비동기 | 실행 한 번 28.6~37.1초(실제 모델, n=4). 90초 이내 95% 를 *제안* (OPERATIONS §2) |
| 비용 | 실행당 상한, 검사 건당 비용 예측 가능 | 상한 [구현]. 측정: 건당 $0.0218 (평가 경로) |
| 감사 | 누가 언제 무엇을 판정·수정·확인했는지 변조를 알아챌 수 있게 | [구현] `ops/audit.py` (한계는 OPERATIONS §6.2) |
| 평가 | "이 도구가 좋다는 걸 어떻게 아나" — 문제 광고를 통과시킨 비율, 문제없는 광고를 괴롭힌 비율, 담당자 확인 없이 끝난 비율 | [구현] `evals/` |

**성공 지표를 먼저 정한 이유:** 정성적 품질("광고 검사가 잘 된다")을 신호로 바꾸지 않으면 모델을 바꿀 때마다 좋아졌는지 알 수 없다. 이 프로젝트는 ① 문제 있는 광고를 통과시킨 건수(가장 중요) ② 문제없는 광고에 수정을 요청한 건수 ③ 담당자 확인 없이 끝난 비율 — 세 가지를 코드로 센다(`evals/metrics.py`).

## 2. 규모 가정 [가정 — 실제 값 아님]

| 항목 | 가정 | 근거 |
|---|---|---|
| 하루 검사 건수 N | 100,000건 (광고 문구 1개 = 1건) | 없음. 계산을 보이기 위한 가정 |
| 평균 도착률 | N ÷ 86,400초 ≈ 1.2건/초 | 계산 |
| 피크 계수 | 5배 → 약 6건/초 | 없음 |
| 건당 모델 호출 | 검사만 약 1.6회 | **측정**: 평가 경로 110건 (`compare_live.json`) |
| 건당 모델 대기 | 중앙값 약 3.0초, 95번째 약 5.8초 | **측정**: 같은 평가 |
| 생성+검사 한 번(광고안 3개) | 모델 호출 11~12회, 28.6~37.1초, $0.11~0.14 | **측정**: 기록된 실제 모델 실행 4건 |
| 건당 비용 | $0.0218 | **측정**: 평가 경로 (gpt-4o 한 제공자) |

계산 (가정 × 측정):
- 동시에 진행 중인 검사 수 ≈ 도착률 × 대기 시간 (리틀의 법칙) = 6건/초 × 3초 ≈ **18건**. 모델 호출을 기다리는 시간이 대부분이라 스레드·비동기로 겹치면 된다. *제공자의 속도 제한이 얼마인지는 확인하지 않았다* — 이 값에 맞춰야 한다.
- 월 비용 ≈ 100,000 × $0.0218 × 30 ≈ **$65,000**. 가정한 N 에 대한 계산일 뿐이며 이 크기에서는 *모델 호출을 줄이는 설계*(§6, §11)가 곧 비용 설계다.
- 우리 코드(모델 호출 제외)의 처리량: 코드 검사 약 590건/초, 예시 실행 파이프라인 약 42건/초 (스레드 1개, 이 환경). 즉 코드 쪽은 병목이 아니고 모델 대기가 병목이다 — `scripts/loadtest.py` 로 *모델 지연을 뺀* 값만 쟀다.

## 4. 요청 경로: 동기와 비동기 [부분 — 동기만 있고 비동기는 설계만]

- **동기(대화형) [부분]:** 화면에서 버튼을 누르면 같은 프로세스가 파이프라인을 끝까지 돌리고 단계마다 진행을 보여 준다(`ui/workbench.py`, `RunOptions.on_progress`). 같은 입력의 3초 내 중복 실행은 막는다. 광고 실행의 전역 동시성·다중 프로세스 조정은 구현하지 않았다. 별도 공동 검수 명령은 DB 행 잠금과 요청 영수증으로 충돌·중복을 다룬다(§9).
- **비동기·배치 [설계만]:** 일괄 업로드는 작업 큐에 넣고 워커가 처리한다. 설계 요점: (1) 작업 ID 와 *멱등성*(같은 문구·같은 조건이면 같은 결과, `recheck_key` 와 같은 발상) (2) 워커 수는 §2 의 동시 진행 수와 제공자 속도 제한에서 정한다 (3) 제공자 호출은 *문구를 묶어* 한 요청에 담는 배치가 가능한지 평가한다 — 묶으면 호출 수는 줄지만 한 건의 오류가 다른 건의 판정에 번질 수 있어 *건별 검증이 가능한 형식*일 때만 한다 (4) 실패한 작업은 지수 백오프로 재시도하되 재시도 횟수와 비용 상한을 둔다(실행당 상한은 [구현]).
- **우선순위 [설계만]:** 대화형 요청은 일괄 요청보다 먼저, 일괄은 남는 용량으로.

## 5. 재검사 캐시 — `recheck_key` [부분]

광고주가 문구를 조금씩 고쳐 가며 다시 검사하는 일이 흔하다. 같은 조건의 *성공한* 결과를 재사용하면 호출을 아낀다.

- **키에 들어가는 것** (`agents/recheck.py` 의 `recheck_key`): 문구(제목·본문·버튼·고지)·주장→근거 연결·상품 정보(이름·업종·사실·설명)·랜딩 문구·반려 이력·검사 기준 버전·프롬프트 버전·실행 방식·모델·자동 판정 기준(τ)·어느 제공자 키가 쓰이는지·교차 확인 사용 여부와 경계 기준·적용 업종·이어받은 근거 사실. **하나라도 다르면 이전 결과를 쓰지 않는다.** 항목마다 따로 해시한 뒤 합쳐 경계가 달라 우연히 같아지는 일을 막는다.
- **실패는 캐시하지 않는다:** 모델 호출이 끝까지 성공한 결과만 재사용(`RecheckResult.reusable`). 실패한 시도는 기록과 사용량을 남기되 같은 문구로 다시 시도한다(`RecheckHistory`).
- **무효화:** 버전(프롬프트·검사 기준)이 키에 있으므로 배포가 곧 무효화다. TTL 은 따로 두지 않았다.
- **지금은** 세션 안의 메모리(`RecheckHistory`)다. **분산 캐시 [설계만]:** 키를 그대로 쓰는 공유 저장소(TTL 포함)로 옮기면 되지만, (1) 광고주 간 캐시 공유는 상품 정보·문구가 키에 들어 있어 서로 다른 광고주가 우연히 같은 키를 갖지 않는다는 점을 확인해야 하고 (2) 캐시된 값에 개인정보가 섞였는지 점검해야 한다. 캐시 적중률 지표는 아직 없다.

## 6. 모델 라우팅과 대체 경로(fallback) [구현] `llm/router.py`, `llm/base.py`

- 작업별 1순위·대신 응답 제공자: 구조화 작업(계획·심사·수리)은 OpenAI→Anthropic, 창의 작업(문구·가상 사용자)은 Anthropic→OpenAI, 교차 확인은 *다른 계열*(Anthropic→OpenAI).
- 서킷브레이커: 연속 3회 실패 → 60초 차단. 차단된 제공자는 건너뛰고 다음으로.
- 형식 오류는 구조화 제공자에게 텍스트→스키마 수리를 한 번 시킨다. 거부(refusal)·잘림(max_tokens, 2배 재시도 1회)은 타입이 있는 예외라 다르게 처리한다.
- 실행당 예산·호출 횟수 상한을 *요청 시도 수*(재시도·수리 포함)에 건다. 넘으면 즉시 중단하고 남은 광고안은 코드 검사만 붙여 담당자 확인으로 남긴다.
- **모델 호출을 줄이는 설계 [설계만]:** 코드 검사가 게재 불가를 *확정*하면 모델이 판정을 뒤집을 수 없다(`decide()` 의 첫 규칙). 평가 사례(개발용 골든셋 55건)의 49%(27건)가 코드 단계에서 게재 불가가 확정됐다. 수정 제안이 필요 없는 경로에서는 검토 모델 호출을 건너뛰는 *단계적(cascade) 설계*가 가능하다. 구현하지 않았고, 실제 광고 구성에서 몇 %인지는 모른다 — 건너뛰면 모델이 주던 설명·수정안을 잃는 대가가 있다.
- **헤징·부하 분산 [설계만]:** 느린 제공자에 같은 요청을 두 곳에 보내는 방식은 비용이 두 배라 쓰지 않는다.

## 7. 속도 제한 [부분]

- **구현:** 서버 키로 도는 실행의 비용 상한(`ui/funding.py`), 화면의 중복 실행 방지, 제공자가 돌려준 429 를 서킷·대체 경로로 흡수.
- **설계만:** 사용자(광고주)별 토큰 버킷, 큐 길이 기반 백프레셔(큐가 차면 일괄 요청부터 거절), 제공자 쿼터를 동시 진행 수로 환산한 전역 세마포어, 비정상 광고주(인젝션·정책 위반 반복) 제한.

## 8. 평가 → 섀도 → 온라인 모니터링 고리 [부분 — 단계마다 표시]

```text
 오프라인 평가 [구현]  ->  회귀 게이트 [구현]  ->  섀도 [설계만]  ->  카나리 [설계만]  ->  온라인 모니터 [구현: 합성에서만 확인]
 evals/ 개발용·최종 확인용        evals/regression.py                      ops/monitors.py
        ^                                                                          |
        |                                                                          v
 평가셋 후보 <- 라벨 [구현] <- 개인·공동 검수 대기열 <- 표본 재검수 [설계만] <- 알림 [설계만]
```

- **개발용/최종 확인용 분리:** 최종 확인용(holdout)은 로직을 고정한 뒤 처음 사용한다. 결과를 읽고 수정에 사용한 자료는 이후 **회귀 검사**로 명시하고 첫 결과·입력·라벨을 보존한다. 기존 라벨은 구현 작성자의 판단이고, 별도 AI가 작성한 합성 자료도 독립 사람 검증은 아니다(`docs/EVALS.md`, [기능별 출처](FEATURES.md)).
- **온라인에서 안전 지표를 재는 법:** 온라인에는 정답이 없다. "문제 있는 광고를 통과시킨 비율"은 자동 판단 건의 *일부를 사람이 다시 보는 표본*으로만 추정할 수 있다 — 이 표본 재검수 절차는 [설계만]이다. 모니터(`ops/monitors.py`)는 정답 없이 볼 수 있는 *대리 신호*(분포·확인율·비용·지연·제공자·인용)를 본다. 대리 신호가 조용해도 안전하다는 뜻이 아니다.
- **라벨링 고리:** 담당자 확인 건 → 대기열 → 라벨·일치도·조정 → 평가셋 후보 → 별도 확인 후 평가셋 편입. `ops/review_queue.py`·`ops/labeling.py`가 라벨 검증과 상태 전이를 맡고, `ops/team_review.py`가 공동 검수의 계정·역할·배정을 강제한다. 개인 브라우저 저장과 서버 공동 저장은 별개다. [LABELING.md](LABELING.md).
- **모니터 → 평가 환류 [설계만]:** 알림이 난 구간과 놓친 변화의 광고를 표본으로 뽑아 라벨링하고 회귀 사례로 추가한다. 장애가 섞인 결과는 기준선·회귀셋에 넣지 않는다(FM-24, 코드가 거부).

**현재 회귀 결과의 읽는 법.** 같은 합성 성과 시나리오 80개에서 변화 탐지는 첫 18/35, 앞선 후속 33/35, 현재 **34/35**다. 현재 정상 사례에 낸 알림은 **0/40**, 원인 1순위·상위 3개는 각각 **30/32**, 기대한 허용 액션 포함은 **77/80**이다. `h26-p077`은 여전히 놓친다. 새 개발용 대조 48개도 지속 하락 **5/12**만 찾고 **7/12**를 놓쳤으며, 정상·추세·회복 대조의 알림은 **0/36**이다. 이는 같은 생성기 위에서 관측을 버리는 경로를 고친 회귀 근거이고 실광고 정확도는 아니다. [현재 80개 결과](../evals/reports/remaining-20261021/insights-after-holdout.json), [대조 결과](../evals/reports/remaining-20261021/insights-contrasts-after.json), [진단과 과거 기록](review-insights-remaining-20261021.md).

**정성 품질의 출처 계약.** `evals/quality_judge.py`는 두 순서의 문구 비교에서 원문 인용·관련 사실·네 기준의 중요도와 선호를 검사하고, 순서 또는 중요한 근거가 다르거나 응답이 부족하면 보류한다. 원시 선택 일치와 실제 채택·보류를 별도 기록한다. 인용의 출처 검사는 의미 판단을 보증하지 않는다. ## 9. 데이터 흐름과 저장 [부분 — 개인·공동 검수 저장은 구현]

서버 공동 DB 기능은 코드와 CI 검증 경로를 준비한 상태다. 실제 운영 DB 초기화·연결은 아직 완료하지 않았으며 활성화한 공동 공간은 **0건**이다.

| 데이터 | 생산 | 소비 | 지금 | 서비스화한다면 [설계만] |
|---|---|---|---|---|
| 요청·광고 문구 | 광고주 | 파이프라인 | 일반 작업은 세션 메모리. 공동 검수에 명시적으로 추가한 문구·사실은 DB에 보존 | 목적별 보존·삭제, 로그에는 해시·길이 |
| 처리 기록(트레이스) | 파이프라인 | 화면·모니터·디버깅 | 세션 메모리 30개, JSON 내보내기 | 객체 저장소 + 인덱스. 프롬프트·응답 원문은 민감 데이터로 분리 |
| 감사 기록 | 어댑터 | 감사·검증 | 요청 시 생성·JSONL | 추가 전용 저장소, 마지막 해시 별도 보관, 키 분리 |
| 지표 | 계산 함수 | 모니터·화면 | 호출 시 계산 | 시계열 저장소 |
| 개인 대기열·라벨·설정 | 개인 검수 화면 | 라벨 도구·평가셋 후보 | 같은 사이트·브라우저 프로필의 IndexedDB, 전체 JSONL 백업 | 개인 백업의 보관·접근 정책 |
| 공동 대기열·라벨·계정·요청 영수증 | 서버 공동 검수 | 역할별 화면·평가셋 후보 | PostgreSQL JSONB 한 행, 서버 권한 검사·행 잠금 | 대규모 분리 저장, 보존·삭제·백업 복원 절차 |
| 평가 결과 | `evals/` | 회귀 게이트·화면 | `evals/reports/*.json` | 버전·데이터 해시와 함께 보관 |

개인정보: 감사 기록은 원문 대신 해시·길이·ID 만 남기고, 실수로 섞인 비밀·연락처 패턴은 저장 전에 가린다(한계는 OPERATIONS §6.3).

**공동 검수의 경계 [구현].** 검수자는 본인에게 배정된 광고를 읽고 제출·반납하며 다른 검수자의 판정은 볼 수 없다. 조정자는 본인이 라벨하지 않은 이견을 조정한다. 관리자는 계정·키·활성 상태와 광고 입력을 관리한다. 계정 ID·역할은 접근키를 통해 서버가 결정한다. DB에는 키 해시만 저장하며 UI의 로그인 키는 세션에만 남긴다. 개인 IndexedDB 저장본을 업로드해 공동 상태를 덮어쓰는 경로는 없다. 이 인증은 공동 검수에 한정되고 전체 공개 앱의 SSO/API 인증이 아니다.

**동시 변경과 응답 유실 [구현].** 공동 저장 경계는 workspace 행을 잠그고, 권한 확인·상태 변경·동일 요청 영수증을 한 트랜잭션에 저장한 뒤 응답한다. 같은 계정·요청 ID·내용의 재시도는 중복 변경을 만들지 않으며, 같은 ID에 다른 내용은 거절한다. 연결 어댑터는 `ops/team_review_store.py`다. 저장 여부를 알 수 없는 오류에서는 UI가 같은 요청을 보존하고 새 변경을 멈춘다. 원자적으로 거절된 입력은 고칠 수 있고, 인증 실패 때에는 로그아웃·키 교체가 가능하다. 세션을 잃으면 UI의 미확인 요청도 없어지므로 서버 상태를 먼저 확인해야 한다.

**DB 권한의 경계 [구현].** 기본 어댑터는 테이블 권한 대신 `lock_workspace`·`save_workspace` 두 함수의 실행 권한을 사용한다. `ops/team_review_db_api.py`가 로그인할 수 없는 함수 소유자, 고정 검색 경로, 공개 실행 권한 회수와 런타임 권한을 설치·검증한다. SQL은 키·만료·활성 상태·역할, 계정 변경 범위와 기존 요청 영수증의 보존을 검사하고, 대기열의 배정·라벨 의미 검증은 Python에 남는다. 유효한 앱 접근키와 런타임 DB 연결 정보가 함께 유출되면 전체 대기열·영수증이 노출되거나 Python 검증을 우회한 대기열 변경이 가능하다. 검수자 간 비공개와 모든 작업 규칙을 DB만으로 강제한다고 주장하지 않는다. 직접 테이블 접근은 명시적인 관리·테스트 경로이며 기본 경로 실패 때 자동 전환하지 않는다.

**규모와 사람 검증의 한계.** 단일 JSONB 행 전체를 읽고 쓰며 잠금 안에서 직렬 처리하는 소규모 구조다. 작업별 행·대규모 병렬 큐·분산 캐시·DB 백업 자동화는 제공하지 않는다. 접근키의 서로 다른 계정을 실제로 다른 사람이라고 인증하지 않으며, 내보내기에도 신원·독립성 미확인을 기록한다. 합성 자료는 기본 제외한다. 관리자 키 회전·유실 복구는 [TEAM_REVIEW.md](TEAM_REVIEW.md), 실패별 화면 동작은 [OPERATIONS.md](OPERATIONS.md) §6.7에 있다.

## 10. 실패 시 동작 — fail-closed [구현]

원칙: **어떤 실패도 승인으로 흐르지 않는다.** 불확실하면 담당자 확인, 확정된 위반은 모델이 뒤집지 못한다.

| 실패 | 동작 | 근거 |
|---|---|---|
| 검토 모델 호출 실패 | 그 광고안은 담당자 확인 (코드 검사에서 확정된 게재 불가는 유지) | `guardrails/failsafe.py`, `agents/adjudicator.py` |
| 제공자 한쪽 장애 | 서킷 + 다른 제공자로 대신 응답 | `llm/router.py` |
| 두 제공자 모두 장애 | 광고안은 담당자 확인으로 쌓임 | FM-07 |
| 비용·호출 상한 초과 | 즉시 중단, 남은 광고안은 코드 검사만으로 담당자 확인 | FM-20 |
| 모델 출력이 형식 오류 | 수리 1회 → 실패 시 단계 실패 → 담당자 확인 | FM-01 |
| 모델이 원문에 없는 인용을 냄 | 경고로 강등, 그 근거만으로는 반려하지 않고 담당자 확인 | FM-04 |
| 모델이 코드가 확정한 사실을 뒤집음 | 그 finding 을 버림 | FM-23 |
| 수정안이 재검사를 통과 못 함 | 수정안 폐기, 원문 판정 유지 | FM-19 |
| 평가 중 제공자 장애 | 장애가 섞인 결과는 기준선·회귀셋 저장 거부 | FM-24 |
| 감사 기록이 가득 참 | 조용히 지우지 않고 오류로 멈춤 | `ops/audit.py` |
| 공동 검수의 저장 결과를 확인하지 못함 | 같은 요청 ID·내용을 보존해 재확인. 새 변경은 중지하고 로그아웃은 허용 | `ui/team_review_view.py`, `ops/team_review_store.py` |
| 공동 검수의 권한·배정·입력 검사 거절 | 원자적으로 거절하고 원인을 표시. 회수·만료된 키로 이전 영수증도 열람할 수 없음 | `ops/team_review.py` |

**담당자 확인 용량이 모자라면?** fail-closed 의 대가는 대기다. 확인 전에는 게재할 수 없으므로 광고주 대기 시간이 늘어난다. 용량 계획 공식은 OPERATIONS §9.

## 12. 구현하지 않은 것

- 실제 **작업 큐·워커**, 비동기 일괄 처리, 우선순위 큐
- **전체 광고 처리 기록·지표의 영속 저장소(DB·객체 저장소)**, 일반 마이그레이션·백업 자동화. 개인 브라우저 저장과 소규모 공동 검수 DB는 구현했다(§9).
- **전체 공개 앱의 SSO·API 인증·권한·감사 로그 접근 통제**, 시크릿 매니저. 공동 검수의 접근키·역할·키 교체·관리자 복구는 구현했으며 적용 범위가 별도다.
- **다중 인스턴스·오토스케일·다중 지역**, 상태 공유(분산 캐시·분산 서킷브레이커 — 서킷 상태는 프로세스 안에 있다)
- **지표 수집기·시계열 저장소·알림 전송**, 대시보드
- **섀도·카나리 트래픽 분할**, 자동 롤백, 배포 파이프라인
- **속도 제한**(사용자별·전역), 백프레셔
- **표본 재검수 절차**(온라인 안전 지표를 재는 방법), 삭제 요청 대응
- 실제 모델의 **장기 지연 분포 측정**(꼬리), 제공자 속도 제한값 확인

## 13. 예상 질문과 답의 뼈대

1. *왜 모델이 아니라 코드가 최종 판정을 하나?* 승인으로 가는 경로에 코드가 검증하는 관문을 두기 위해서다. 모델은 확신 있게 틀린다(FM-14) — 인용이 원문에 있는지·값이 입력에 있는지 코드가 대조하고, 확신이 낮거나 못 읽으면 통과가 아니라 담당자 확인으로 간다.
2. *이 시스템이 좋다는 걸 어떻게 아나?* 문제 광고 통과 건수, 문제없는 광고 괴롭힘, 담당자 확인 없이 끝난 비율을 라벨된 사례로 센다. 한계: 라벨과 규칙을 같은 저자가 썼고, 개발용 사례는 규칙을 고치는 데 썼다. 최종 확인용(holdout)은 규칙을 고정한 뒤 처음 썼다. 그래도 표본이 작다(12건).
3. *실서비스에서 가장 먼저 깨질 곳은?* 담당자 확인 용량(fail-closed 의 대가), 제공자 속도 제한(미확인), 평가 사례와 실제 광고 구성의 차이. 모니터는 이 중 앞의 둘을 *대리 신호*로 본다.
4. *온라인에서 안전을 어떻게 지키나?* 정답이 없으므로 표본 재검수(설계만)가 필요하고, 모니터는 분포·확인율·비용·지연·제공자·인용 신호로 이상을 알린다. 합성 스트림 시뮬레이션으로 탐지 지연과 오경보율을 쟀지만 실제 트래픽에서의 성능은 모른다.
5. *비용을 어떻게 줄이나?* 실행당 상한(구현), 재검사 캐시(부분), 교차 확인은 경계 사례만(구현), 코드가 게재 불가를 확정한 건은 모델 호출을 건너뛰는 단계적 설계(설계만, 효과 미측정).
6. *제공자가 죽으면?* 서킷 + 다른 제공자로 대신 응답, 둘 다 죽으면 광고안이 담당자 확인으로 쌓임. 검사를 건너뛰고 통과시키는 우회는 없다.

## 14. 설명할 때 하지 말아야 할 주장

- 서비스를 이미 굴리고 있다는 인상을 주는 표현. 이것은 시뮬레이션과 평가 사례로 장치를 확인한 개인 프로젝트다.
- 효과 모델의 절감 시간·인건비 환산을 "얻은 성과"로 말하는 것 — 가정을 넣은 계산이며 모든 결과에 "실제 운영 효과가 아님"이 붙는다.
- 합성 스트림의 탐지율·지연을 실제 성능으로 말하는 것.
- 예시 실행(대역)의 비용·지연을 모델의 값으로 말하는 것.
- 처리량 측정을 서비스 용량으로 말하는 것 (모델 지연이 빠져 있다).
