# 운영 문서

이 문서는 **이 도구를 서비스로 내보낸다면 무엇이 필요한가**를 적고, 그중 코드로 만들 수 있는 것은 만들어 시뮬레이션으로 확인한 결과를 함께 적는다.

> **먼저 읽을 것.** 이 프로젝트에는 실제 서비스의 운영 데이터가 없다. 실제 광고주의 요청을 받은 적도, 서비스로 배포해 장애를 처리한 적도 없다(평가 실행 중 제공자 크레딧이 떨어져 호출이 실패한 일은 있었고 FM-24 로 기록했다).
> 아래의 SLO·임계값·용량 공식·롤아웃 기준은 *제안*이고, 모니터와 감사 기록은 *합성 데이터로 동작을 확인한 장치*다. 실제 트래픽에서 맞는지는 검증되지 않았다.
> 숫자마다 **측정**(이 저장소에서 실제로 잰 값) · **가정**(이 프로젝트가 정한 값, 근거 없음 또는 약함) · **제안**(운영을 시작한다면 쓸 시작값)을 구분해 적었다.

절마다 상태를 표시한다.

| 표시 | 뜻 |
|---|---|
| **[구현]** | 코드와 테스트가 있다. |
| **[부분]** | 일부만 코드가 있고 나머지는 설계다. |
| **[제안]** | 코드 없이 정한 기준·절차다. |
| **[설계만]** | 필요하다고 생각하지만 만들지 않았다. |

## 2. 서비스 수준 목표(SLO) 제안 [제안]

목표는 *시작값*이다. 실제 분포를 충분히 잰 뒤 다시 정한다.

| 지표 | 제안 목표 | 근거 | 측정 방법 | 상태 |
|---|---|---|---|---|
| 실행 한 번의 처리 시간 | 90초 이내 95% | **측정**: `traces/` 에 기록된 실제 모델 실행 4건이 28.6~37.1초(n=4)였다. 약 2.4배 여유를 둔 *가정*이다. 분포의 꼬리는 잰 적이 없다 | `latency_slo_burn` (§4.1.4) | 모니터 [구현], 목표값 [제안] |
| 실행이 끝까지 정상 종료(중간 멈춤·일부 단계 실패 없음) | 98% 이상 | 근거 없음. 시작값 | `n_halted`, `FM-05·06·07·20` 건수 | 지표 [구현], 목표값 [제안] |
| 문제 있는 광고를 담당자 확인 없이 통과시킨 비율 | 표본 재검수에서 상한 5% 이하 | **측정**: 평가 사례 76건 중 0건, 윌슨 95% 상한 4.8%(`compare_live.json`). 온라인에서는 정답이 없어 직접 잴 수 없다 → 자동 판단 건의 일부를 사람이 다시 보는 표본 검수가 필요하다 | 표본 검수 결과 (§9의 재확인 비율 `s`) | 표본 검수 절차 [설계만], 목표값 [제안] |
| 담당자 확인으로 넘기는 비율 | 15% 이하 | **측정**: 평가 사례 110건 중 8건 7.3%(95% 구간 3.7~13.7%). 문제없는 광고만 보면 34건 중 5건(14.7%). 이 측정은 교차 확인(다른 모델 계열)이 없는 평가 경로의 값이라 실제 파이프라인에서는 더 높을 수 있다. 실제 광고 구성도 모른다 | `human_review_surge` (§4.1.2) | 모니터 [구현], 목표값 [제안] |
| 담당자 확인 건의 응답 시간 | 우선순위별 SLA (`ops/review_queue.py` 의 `sla_hours`) | 다른 담당 파일에 *가정*으로 정의됨. 이 문서는 값을 정하지 않는다 | 대기열 통계 | 대기열 [구현, 다른 담당], 목표값 [제안] |
| 실행당 비용 | 중앙값 $0.15 이하, 하드 상한 $0.50 | **측정**: 실제 모델 실행 4건이 $0.11~0.14. 하드 상한 $0.50 은 `PREFLIGHT_RUN_BUDGET_USD` 기본값(**구현**) | `cost_anomaly` (§4.1.3), `FM-20` | 상한 [구현], 중앙값 목표 [제안] |

오류 예산: 지연 SLO 는 95% 목표라 실행의 5%까지 느려도 예산 안이다. `latency_slo_burn` 은 이 예산을 *정해진 속도의 몇 배로* 쓰는지를 본다(번 레이트).

## 3. 지표와 모니터링

### 3.1 지표 (`ops/metrics.py`) [구현]

| 지표 | 계산 방법 | 주의 |
|---|---|---|
| 판정 분포·담당자 확인율 | 광고안별 최종 판정 건수 | 한 실행의 광고안들은 서로 닮는다 |
| 단계별 지연 p50/p95/p99 | 트레이스 스팬의 실제 경과 시간 | n 이 100 미만이면 p99 는 최댓값에 가깝다 |
| 실행당·광고안당 비용 | `PipelineRun.total_cost_usd` | 응답을 받지 못한 요청이 있으면 최소값(`cost_is_lower_bound`) |
| 제공자별 응답·실패·대신 응답(fallback)·서킷 차단 | 모델 호출 스팬의 이벤트 | 예시 실행(mock)은 `synthetic` 표시, 실패율에 넣지 않음 |
| 실패 모드(FM) 빈도 | `PipelineRun.failures` | — |
| 고친 문구 재검사 사용률 | 이름이 `recheck` 인 트레이스 수 ÷ 광고안 수 | — |
| 검토 모델 인용이 원문에 없던 비율 | 의미 검사 계층 finding 의 `verified_quote=False` 비율 | FM-04 와 같은 사건 |

`Metrics.to_prometheus_text()` 는 표준 텍스트 노출 형식(라벨 값 이스케이프 포함)을 낸다. **수집기·시계열 저장소·대시보드는 없다** — 형식만 맞춘 것이다 [설계만].

### 3.2 모니터 규칙 (`ops/monitors.py`) [구현]

입력은 실행 기록 스트림과 기준 구간이다. 표본이 모자라면 판단하지 않고 *보류*한다(보류는 정상이 아니다).

| 규칙 | 보는 것 | 임계값 | 최소 표본 | 최대 심각도 | 런북 |
|---|---|---|---|---|---|
| `verdict_drift` | 판정 분포 변화 | PSI ≥ 0.10 주의, ≥ 0.25 심각, 그리고 카이제곱 p < 0.001 | 창 광고안 100·기준 200 | 심각 | §4.1.1 |
| `human_review_surge` | 담당자 확인율 급증 | 창 비율의 윌슨 95% 하한 > max(기준×2, 기준+0.05) | 창 100·기준 200 광고안 | 주의 | §4.1.2 |
| `cost_anomaly` | 실행당 비용 | 창 중앙값의 로버스트 z ≥ 4.0 이고 기준 중앙값의 1.25배 이상 | 창 20·기준 30 실행 | 주의 | §4.1.3 |
| `latency_slo_burn` | 지연 SLO 오류 예산 소진 속도 | 긴 창(60)과 짧은 창(12)이 함께 번 레이트 ≥ 2 주의, ≥ 6 심각 | 긴 창 30·짧은 창 6 | 심각 | §4.1.4 |
| `provider_failure_surge` | 제공자(별) 실패율 | 창 실패율의 윌슨 하한 > max(기준×3, 기준+0.05) | 창 30·기준 100 호출 | 심각 | §4.1.5 |
| `citation_surge` | 원문에 없는 인용 비율 | 창 비율의 윌슨 하한 > max(기준×2, 기준+0.05) | 창 30·기준 100 근거 | 주의 | §4.1.6 |

**임계값의 근거는 모두 *가정*이다.** PSI 0.1/0.25 는 신용 모형 모니터링 관행의 경험칙, 로버스트 z 는 중앙값·MAD 이상치 규칙, 번 레이트 배수는 SRE 의 다중 창 번 레이트 관행에서 빌렸다. 이 프로젝트의 데이터로 보정하지 않았다. 지연 SLO 90초·목표 95% 는 §2 의 가정이다.

### 3.3 탐지 지연과 오경보 — 합성 스트림 시뮬레이션 [구현]

**이 표가 말하는 것:** 이 프로젝트가 정한 예시 분포(§3.3.1)의 합성 스트림에서, 위 규칙이 변화를 *얼마나 빨리, 몇 %* 알아채고 변화가 없을 때 *얼마나* 잘못 울리는가.
**말하지 않는 것:** 실제 서비스에서의 탐지 성능. 실제 트래픽의 분포·변화 크기·실행 간 상관은 모른다.

재현: `python -m ops.monitors --streams 100 --runs 300 --change-at 180 --baseline 100 --seed 2026 --eval-every 1`
(스트림 100개 × 실행 300건. 앞 100건이 기준 구간, 180번째 실행부터 변화, 매 실행 뒤 평가. 같은 시드면 같은 결과.)

| 상황 (변화 크기는 예시) | 기대 규칙 | 알아챈 스트림 | 변화 후 몇 건 만에 (중앙값 / 90번째 / 최대) | 기대 밖 규칙도 울린 스트림 |
|---|---|---|---|---|
| 판정 분포 보통 이동 (통과 40→25%, 반려 20→35%) | `verdict_drift` | 88/100 | 44.5 / 85 / 119 | 없음 |
| 판정 분포 크게 이동 (통과 40→20%, 반려 20→45%) | `verdict_drift` | 100/100 | 32 / 41 / 49 | 없음 |
| 담당자 확인 10→25% | `human_review_surge` | 73/100 | 48 / 89 / 118 | `verdict_drift` 94 |
| 한 제공자 실패율 1→50%, 지연 2.5배 | `provider_failure_surge` | 100/100 | 8 / 10 / 12 | `latency_slo_burn` 100 |
| 실행당 비용 3배 | `cost_anomaly` | 100/100 | 20 / 23 / 25 | `verdict_drift` 1 |
| 처리 시간 2배 | `latency_slo_burn` | 100/100 | 36 / 52 / 86 | `verdict_drift` 1 |
| 원문에 없는 인용 4→20% | `citation_surge` | 100/100 | 30 / 45 / 73 | `verdict_drift` 2 |

**오경보** (변화 없는 정상 스트림 100개 × 평가 200회). 오경보 0 을 요구하지 않았고, 나온 만큼 적는다.

| 규칙 | 한 번이라도 울린 스트림 | 95% 구간 | 에피소드 수 |
|---|---|---|---|
| `verdict_drift` | 4/100 | 1.6~9.8% | 7 |
| `human_review_surge` | 1/100 | 0.2~5.5% | 3 |
| `cost_anomaly` · `latency_slo_burn` · `provider_failure_surge` · `citation_surge` | 각각 0/100 | 각각 0~3.7% | 0 |

읽는 법과 한계:
- 담당자 확인 25% 급증은 27%를 놓쳤다(창 150광고안의 신뢰구간 때문). 이 상황은 확인 비율을 올리면서 다른 칸 비율도 함께 줄이도록 만들었기 때문에 판정 분포 규칙(`verdict_drift`)이 94%에서 같이 울렸다 — 확인 비율만 단독으로 오르는 변화는 따로 시험하지 않았다.
- `verdict_drift` 의 오경보 4%/스트림(에피소드 7회)은 이 설정에서 가장 크다. 실행 안의 광고안이 닮아 광고안을 독립으로 센 통계가 낙관적이기 때문으로 *추정*한다(원인을 따로 검증하지는 않았다). 실제 트래픽의 닮음은 더 클 수 있어 오경보도 더 많을 수 있다.
- 오경보 0건이라고 적힌 칸은 "100개 스트림에서 0건"이라는 뜻이지 오경보가 없다는 뜻이 아니다(95% 상한이 3.7%).
- 처음 만든 규칙을 시드 0·1 의 작은 실행으로 동작만 확인하고, 임계값은 시뮬레이션 *전에* 정했다. 위 표는 시드 2026 에서 처음 돌린 결과다. 기준 스트림의 지연·비용 중앙값은 기록된 실제 모델 실행 4건에 맞춰 한 번 고쳤다(탐지 성능과 무관한 수정).

#### 3.3.1 시뮬레이션의 가정 (모두 예시)

판정 확률 통과 .40·수정 .30·반려 .20·담당자 확인 .10, 실행당 광고안 3개(실행마다 디리클레로 흔들어 닮음을 흉내, 집중도 20), 실행 지연 중앙값 33초(σ=0.35, 기록된 실제 모델 실행 4건의 가운데), 실행 비용 중앙값 $0.12(σ=0.25, 같은 4건), 제공자 호출 openai 8±2·anthropic 4±2회 실패율 1%, 실행당 검토 근거 1~5개 중 원문에 없는 비율 4%. 이 값들 중 **측정에서 온 것은 지연·비용의 중앙값뿐**(n=4)이고 나머지는 지어낸 예시다.

### 3.4 수집과 보관 [설계만]

지표를 주기적으로 긁어 시계열 저장소에 쌓고, 알림 규칙(§3.2)을 거기서 평가하고, 호출 도구·메신저로 보내는 부분은 만들지 않았다. 지금은 화면(`ui/ops_view.py`)과 함수 호출로 *그 시점의 스냅숏*만 계산한다. 기준 구간을 어떻게 갱신할지(고정·이동 평균)도 정하지 않았다 — 기준 구간 자체가 비정상이면 그 비정상을 정상으로 배운다.

## 4. 알림과 런북

### 4.1 모니터 규칙별 런북 [제안]

각 규칙이 울리면 이 순서로 본다. 절 번호는 `ops/monitors.py` 의 `RULE_SPECS[...].runbook` 과 같다(테스트가 대조).

#### 4.1.1 판정 분포 변화 (`verdict_drift`)
- **뜻:** 통과·수정·반려·담당자 확인의 구성이 기준 구간과 다르다. 입력(광고주·업종) 변화일 수도, 모델·프롬프트·검사 기준 변화일 수도, 장애로 인한 담당자 확인 쏠림일 수도 있다.
- **먼저 볼 것:** 어느 칸이 움직였나(`detail.window` vs `detail.baseline`). 같은 시기 배포(프롬프트 버전·검사 기준 버전은 트레이스 `metadata` 에 있다), 제공자 실패율(§4.1.5), 업종별 구성.
- **조치:** 최근 배포가 원인이면 롤백(§5.5). 입력 변화면 정상일 수 있다 — 표본 재검수로 판정이 맞는지 확인한 뒤 기준 구간을 갱신한다. 담당자 확인 쪽이 늘었다면 §4.1.2.
- **심각:** 반려가 급감하고 통과가 늘었다면 안전 문제 가능성 — 즉시 표본 재검수(통과 건 우선), 롤백 검토.

#### 4.1.2 담당자 확인 비율 급증 (`human_review_surge`)
- **뜻:** 자동으로 확정하지 못한 비율이 올랐다 → 검수 인력 필요량이 같은 비율로 는다(§9).
- **먼저 볼 것:** FM-17(두 모델 계열 불일치), FM-05·06·07(제공자 실패로 담당자 확인으로 떨어짐), FM-04·23(모델 근거 문제), 특정 업종 쏠림.
- **조치:** 제공자 장애가 원인이면 §8, 복구 후 대기열 재처리. 모델·프롬프트 변경이 원인이면 롤백. 원인이 입력 변화면 대기열 우선순위(`ops/review_queue.py`)와 인력 조정(§9).
- **주의:** 자동 판정 확신 기준(τ)을 낮춰 확인율을 억지로 줄이지 않는다 — 안전 지표(문제 있는 광고 통과)가 먼저다.

#### 4.1.3 실행당 비용 이상 (`cost_anomaly`)
- **뜻:** 실행당 비용 중앙값이 기준보다 통계적으로도 크고 1.25배 이상이다.
- **먼저 볼 것:** FM-20(비용·호출 상한), 재시도·수리·재생성 증가(FM-01·16), 모델 라우팅 변경, 광고안 수 설정, 재검사 캐시 적중 감소.
- **조치:** 모델·가격표(`observability/pricing.py`) 변경 확인, 호출 상한(`max_calls`)·실행당 예산(`PREFLIGHT_RUN_BUDGET_USD`) 확인. 일시적이면 관찰, 지속이면 원인 되돌림.
- **참고:** 기준 구간 비용이 0이면(예시 실행) 이 규칙은 보류된다.

#### 4.1.4 처리 시간 SLO 번 레이트 (`latency_slo_burn`)
- **뜻:** 90초 이내가 아닌 실행이 오류 예산(5%)을 2배(주의) 또는 6배(심각) 이상의 속도로 쓰고 있다. 긴 창과 짧은 창이 *함께* 넘어야 울린다(일시적 튐을 거른다).
- **먼저 볼 것:** 제공자 응답 지연(`llm_latency_ms`), 단계별 지연(어느 단계가 늘었나), 제공자 실패에 따른 대신 응답(fallback)·재시도, 동시 실행 증가.
- **조치:** 제공자 문제면 §4.1.5·§8. 우리 코드 쪽이면 `scripts/loadtest.py` 로 코드 구간 지연을 재서 비교한다(모델 지연이 빠진 값이다).

#### 4.1.5 제공자 실패 급증 (`provider_failure_surge`)
- **뜻:** 한 제공자의 호출 실패율이 기준의 3배(그리고 +5%p) 이상이다. 서킷브레이커(연속 3회 실패 → 60초 차단)와 대신 응답 경로가 이미 돌고 있을 수 있다.
- **먼저 볼 것:** 제공자 상태 공지, 429(FM-06)인지 타임아웃(FM-05)인지, `circuit_skips`, 대신 응답 비율, 두 제공자가 모두 나쁜지(FM-07).
- **조치:** 한쪽만 나쁘면 대신 응답 경로가 흡수하는지 지연·비용을 확인. 둘 다 나쁘면 §8 장애 대응(검사하지 못한 광고는 *통과가 아니라 담당자 확인*으로 쌓인다 — fail-closed).
- **금지:** 실패를 이유로 검사를 건너뛰고 통과시키는 우회 설정은 만들지 않는다.

#### 4.1.6 원문에 없는 인용 비율 급증 (`citation_surge`)
- **뜻:** 검토 모델이 "이런 구절이 있다"고 한 근거 중 원문에서 못 찾는 비율이 올랐다(FM-04). 코드가 이미 강등·담당자 확인으로 처리하므로 안전은 유지되지만 모델 품질 저하 신호다.
- **먼저 볼 것:** 모델·프롬프트 버전 변경, 입력 길이·언어 변화, 제공자 대신 응답(다른 모델이 응답 중인가).
- **조치:** 변경이 원인이면 롤백. 아니면 평가 사례로 같은 모델의 인용 비율을 다시 재 본다(`evals`).

### 4.2 실패 모드별 런북 [제안]

`guardrails/failure_modes.py` 의 모든 코드를 한 줄씩 연결한다. "신호"는 이 저장소에서 실제로 계산되는 지표 또는 모니터다. 새 실패 모드가 카탈로그에 추가되면 이 표에도 행을 추가한다.

FM-25 이후는 기능(대화형 셋업 FM-25~40, 상품 페이지 가져오기 FM-41~55, 이미지 FM-56~73, 소재 퀄리티 FM-74~83, 성과 리포트 FM-84~97, 라벨링·검수 FM-98~119, 운영 FM-120~131)을 더하면서 같은 번호 체계로 이어 붙인 코드다. 행은 카탈로그의 탐지·방어와 같은 내용을 "무엇으로 알아채고 → 먼저 무엇을 하나" 로 옮겼다. 두 가지를 구분해서 읽는다.
- FM-25~28 은 대화 결과(`TurnResult.failures`)에 `FailureEvent` 로 남는다. `ops/metrics.py` 의 실패 모드 집계는 광고 작업 실행(`PipelineRun.failures`)만 세므로 이 네 코드는 거기에 잡히지 않는다.
- 나머지 새 코드는 `FailureEvent` 로 남기지 않는 방어선이다. "신호" 칸에는 그 기능의 평가 지표나 결과 필드를 적었고, 그런 것이 없으면 "런타임 지표 없음" 이라고 적었다(해당 테스트가 곧 신호다).
- `fail_closed` 가 거짓인 코드(FM-40, 45, 46, 55, 62, 67, 84, 90, 109, 112, 121, 122)는 알려진 한계가 남아 있다. 첫 조치 칸에 그 한계를 다시 적었다.

## 5. 롤아웃 계획 [제안]

코드로 *구현된* 것은 1단계의 회귀 게이트와 평가 도구뿐이다. 섀도·카나리·확대의 트래픽 분할, 자동 롤백은 [설계만]이다. 아래 통과 기준의 수치는 시작값이며 근거가 약하다.

### 5.1 1단계 — 오프라인 평가 [부분]
- **하는 일:** 개발용 평가셋 회귀 게이트(`evals/regression.py`), 최종 확인용(holdout)과 방식 비교(`evals/compare.py`), 레드팀(`evals/redteam.py`).
- **통과 기준(제안):** (a) 회귀 게이트 통과 (b) holdout 에서 문제 있는 광고 통과 0건이고 윌슨 상한을 보고 (c) 담당자 확인율이 직전 버전 대비 악화 없음 (d) 호출 실패가 섞이지 않은 결과일 것 (e) 실행당 비용이 §2 범위.
- **롤백 조건:** 하나라도 미달이면 배포하지 않는다. holdout 은 로직을 고정한 뒤 한 번 보고, 결과를 보고 고치지 않는다.
- **한계:** 라벨과 규칙을 같은 저자가 만들었고 독립 검증자가 없다. 평가 사례 구성은 실제 광고의 구성이 아니다.

### 5.2 2단계 — 섀도 모드 [설계만]
- **하는 일:** 실제 요청을 받되 *결과를 광고주에게 쓰지 않고* 기존 절차(사람 검수)의 결정과 나란히 기록한다. AI 판정과 사람 최종 판정의 불일치를 모은다.
- **통과 기준(제안):** 최소 1,000건 이상(근거 없음, 윌슨 상한이 의미 있을 만큼); AI 가 통과시킨 건 중 사람이 문제로 본 비율의 95% 상한이 §2 목표 이하; 지연·비용 SLO 충족; 담당자 확인율이 오프라인 측정 구간 안.
- **롤백 조건:** 문제 있는 광고 통과가 1건이라도 확인되면 원인 분석 전까지 다음 단계로 가지 않는다.

### 5.3 3단계 — 카나리 [설계만]
- **하는 일:** 트래픽의 1% → 5% → 25% 순으로 AI 판정을 *실제로 적용*(담당자 확인 건은 사람). 단계마다 최소 관측 건수와 기간(제안: 단계당 하루 이상, 500건 이상)을 채운 뒤 넘어간다.
- **통과 기준:** §3.2 모니터가 심각 없이 유지, 표본 재검수에서 문제 통과 없음, 담당자 확인 대기 SLA 충족.
- **롤백 조건:** 심각 알림 1건 지속(10분 이상), 문제 있는 광고 통과 확인 1건 이상, 대기 SLA 연속 위반.

### 5.4 4단계 — 확대 [설계만]
- 100%로 확대하되 표본 재검수와 롤백 스위치를 유지한다. 모델·프롬프트·검사 기준을 바꿀 때마다 1~3단계를 다시 거친다(버전은 재검사 캐시 키에 들어 있어 이전 결과가 새 버전에 재사용되지 않는다 — `agents/recheck.py` 의 `recheck_key`).

### 5.5 롤백 방법 [부분]
- 프롬프트 버전(`agents/prompts.py` 의 `PROMPT_VERSION`)·검사 기준 버전(`guardrails/policy.yaml`)·모델 이름(`OPENAI_MODEL`·`ANTHROPIC_MODEL` 환경변수)은 코드·설정으로 고정돼 있어 이전 값으로 되돌릴 수 있다. 되돌리는 *배포 절차 자체*(이미지·설정 배포 파이프라인)는 이 프로젝트에 없다 [설계만].

| 광고주 요청·상품 설명·랜딩 문구 | 세션 메모리. 개인정보가 섞일 수 있다 | 보존하지 않거나 짧게. 로그에는 해시·길이만 |
| 광고 문구·판정 결과 | 세션 메모리 | 판정 결과는 보존, 원문은 목적 범위 안에서 |
| 처리 기록(트레이스) | 세션 메모리(최대 30개), 내려받기 시 사용자가 받음. **프롬프트·응답 원문이 들어 있어 민감** | 짧은 보존(예: 수 주, 근거 없는 자리표시자), 접근 제한 |
| 감사 기록 | 요청 시 생성(`ops/audit.py`). 원문 대신 해시·길이·ID | 추가 전용 저장소, 마지막 해시 별도 보관 |
| 라벨 | `ops/review_queue.py`(다른 담당) | 라벨러 식별자는 가명 처리 |
| API 키 | 서버 환경변수에서만 읽음. 화면·세션 상태·처리 기록·내려받기에 나오지 않음(기존 테스트 `tests/test_app.py`) | 시크릿 매니저 [설계만] |

### 6.2 감사 기록 (`ops/audit.py`) [구현]
- 항목마다 앞 항목의 해시를 이은 해시 체인(SHA-256, 키 정렬 JSON). 중간 수정·삭제·순서 바꿈·앞쪽 잘림을 처음 틀어진 위치와 함께 알린다.
- **알아채지 못하는 것:** (1) 끝을 잘라 낸 기록 — 마지막 해시와 항목 수를 *따로* 보관하고 대조해야 잡힌다. (2) 공격자가 모든 해시를 처음부터 다시 계산해 쓴 기록 — 마지막 해시를 따로 보관하거나, 키로 만든 체인(HMAC)을 쓰고 키를 기록과 분리해 보관해야 막힌다. **키 보관 장치는 이 프로젝트에 없다.** (3) 파일을 쓰지 못하게 막는 것(변조 방지)은 하지 않는다. 테스트가 (1)(2)를 "못 잡는다"는 사실까지 고정한다.
- **크기·개수 정책:** 가득 차면 오래된 것을 밀어내지 않고 `AuditFull` 오류로 멈춘다(압축도 하지 않는다). 한 항목이 16KiB 를 넘으면 `EntryTooLarge`. 가득 찬 기록은 내보낸 뒤 `AuditLog.continue_from()` 으로 마지막 해시를 이어받아 새 구간을 시작하고, 이어 검증할 때 앵커(시작 순서, 앞 구간의 마지막 해시)를 넘긴다.
- **기록하는 사건:** 작업 실행(`run.executed`)·판정(`ad.judged`)·자동 수정안 재검사(`ad.rewrite_checked`)·사람의 문구 수정(`ad.edited`)·재검사(`ad.rechecked`)·담당자 확인 요청/결과(`human.review_requested`/`human.review_decided`)·라벨 제출(`label.submitted`).

### 6.3 마스킹의 한계
저장 전에 API 키(`sk-…`·`sk-ant-…`·알려진 접두사)·영문숫자 32자 이상 토큰·이메일·전화번호·주민등록번호 형태·카드번호(루훈 검사 통과)를 가린다. **이 패턴에 안 걸린 것은 가려지지 않는다** — 이름·주소·계좌번호·자유 서술 속 개인정보·전각 숫자나 띄어 쓴 번호는 못 잡는다. 그래서 1차 방어는 *애초에 넣지 않는 것*이다: 어댑터는 광고 원문 대신 해시·길이·규칙 ID 만 남긴다. 패턴이 넓어 과하게 가린다(예: 날짜처럼 보이는 13자리 숫자는 주민등록번호 형태로 간주). 마스킹 규칙은 `tests/test_ops_audit.py` 가 고정한다.

### 6.4 삭제 요청과 해시 체인 [설계만]
해시 체인은 항목을 지우면 깨진다. 그래서 개인정보를 항목에 직접 넣지 않는 설계(해시·ID)를 택했다. 개인정보를 꼭 남겨야 한다면 항목에는 암호화된 값만 넣고 키를 폐기하는 방식(crypto-shredding)이 필요하다 — 만들지 않았다.

## 7. 비용 통제

### 7.1 이미 있는 장치 [구현]
- **실행당 예산 상한**(`PREFLIGHT_RUN_BUDGET_USD`, 기본 $0.50)과 **호출 횟수 상한**(`RunBudget.max_calls`, 기본 60)은 *요청 시도 수*(실패·재시도·수리 포함)에 걸린다. 넘으면 `BudgetExceeded` 로 중단하고 검사 못 한 광고안은 담당자 확인으로 남는다(FM-20).
- **서버 키 비용 상한**: 서버가 가진 키가 쓰이면 서버가 정한 상한이 적용된다(`ui/funding.py`). 상한이 0이면 실제 모델 실행이 막힌다.
- **모델 라우팅**: 작업별 1순위·대신 응답 제공자(`llm/base.py` 의 `ROUTING`). 교차 확인(두 번째 모델)은 *경계 사례에만* 호출한다.
- **재검사 캐시**: 같은 조건의 *성공한* 재검사 결과만 재사용한다(`recheck_key` — 문구·상품 정보·검사 기준·프롬프트·모델·기준값이 하나라도 다르면 다시 검사). 실패한 결과는 재사용하지 않는다.
- **실행 전 확인**: 평가 실행은 예상 호출 수·비용을 보여 주고 확인 뒤에만 돈다.

### 7.2 관측된 비용 (측정)
- 실제 모델 처리 기록 4건: 실행당 $0.11~0.14, 모델 호출 11~12회.
- 방식 비교 평가(사례 110건, `compare_live.json`): 합친 방식 사례당 $0.0218(호출 약 1.6회), 검토 모델만 사례당 $0.0121, 코드 검사만 $0.
- 이 값은 gpt-4o 한 제공자로 잰 것이고 가격표는 근사치다(`observability/pricing.py`).

### 7.3 제안 [설계만]
일·월 예산 알림(지금은 *실행당* 상한만 있다), 캐시 적중률 지표, 모델 다운시프트(싼 모델로 먼저 거르기)의 평가, 제공자별 월 한도. 월 비용 ≈ (일 검사 건수) × (건당 비용) × 근무일 — 건당 비용은 위 측정값, 건수는 가정(`ops/impact.py` 가 같은 식을 쓴다).

## 8. 장애 대응 절차 [제안]

### 8.1 심각도 (제안)
| 등급 | 기준 | 예 |
|---|---|---|
| SEV1 | 문제 있는 광고가 통과했을 가능성, 또는 검사가 전면 중단 | 표본 재검수에서 통과 확인, 제공자 전체 장애가 길어짐 |
| SEV2 | 기능 저하(지연 SLO 번 레이트 심각, 제공자 한쪽 장애) | `latency_slo_burn` 심각 |
| SEV3 | 비용·품질 신호(주의 알림) | `cost_anomaly`, `citation_surge` |

### 8.2 절차
1. **탐지:** 알림(§4) 또는 표본 재검수.
2. **분류:** 어느 규칙·실패 모드인가(§4.2). 최근 배포(프롬프트·검사 기준·모델)와 시간이 겹치는가.
3. **완화:** 검사는 *fail-closed* 로 동작한다 — 어떤 실패도 통과로 흐르지 않고 담당자 확인으로 쌓인다(`guardrails/failsafe.py`). 따라서 완화의 핵심은 대기열이 넘치지 않게 하는 것(§9)이다. 우회(검사 생략)는 하지 않는다.
4. **복구:** 원인 되돌림(§5.5) 또는 제공자 복구. 복구 후 쌓인 담당자 확인 건 재처리.
5. **사후 분석:** 무엇이 먼저 울렸나, 탐지까지 얼마나 걸렸나, 놓친 신호는 무엇인가, 새 실패 모드를 `guardrails/failure_modes.py` 에 추가할 것인가, 회귀 사례로 추가할 것인가.

### 8.3 장애 훈련 [구현]
`Router.simulate_failure(provider, kind)` 와 광고 작업 화면의 장애 시뮬레이션 옵션으로 타임아웃·레이트 리밋·거부·형식 오류를 일부러 일으켜 대체 경로를 볼 수 있다. 훈련은 광고 작업에만 적용되고 평가 실행에는 적용되지 않는다(`app.router_factory`).

## 9. 사람 검수 용량 계획

코드: `ops.impact.required_reviewers`, `erlang_c`, `mean_wait_minutes`. 아래 값은 모두 **가정**을 넣어 계산한다.

기호: N 하루 검사 건수, h 담당자 확인율, t_f 담당자 확인 건 처리 시간(분), s 자동 판단 건을 사람이 다시 보는 비율, t_r 사람이 직접 검수할 때 1건 시간(분), H 하루 근무 시간, ρ 가동률(회의·휴식·전환을 뺀 실제 검수 비율), k 피크 계수(가장 바쁜 시간대가 평균의 몇 배인가).

- 하루 검수 시간(분) = N · [ h · t_f + (1 − h) · s · t_r ]
- 필요 인원(FTE) = 하루 검수 시간 ÷ (H · 60 · ρ) · k
- 대기: 도착률 λ = N·h/(H·60) (분당), 처리율 μ = 1/t_f, 이용률 u = λ/(c·μ) (c 명). **u ≥ 1 이면 대기열이 끝없이 쌓인다.** 평균 대기 시간은 M/M/c 근사(Erlang C)로 본다 — 도착이 무작위이고 처리 시간이 지수 분포라는 단순 가정이며 실제 대기 시간이 아니다.

계산 예 (**가정**: N=200, t_f=8, s=0.05, t_r=5, H=8, ρ=0.7, k=1; h 는 **측정** 7.3% 와 그 95% 구간):

| h | 필요 인원 | 1명이 처리할 때 평균 대기 | 피크 3배일 때 1명 평균 대기 |
|---|---|---|---|
| 3.7% (구간 하한) | 0.32명 | 약 1.1분 | 약 4.8분 |
| 7.3% (측정 점추정) | 0.48명 | 약 2.6분 | 약 21.3분 |
| 13.7% (구간 상한) | 0.78명 | 약 6.7분 | 한 명으로는 감당 불가(이용률 ≥ 1) |

읽는 법: 필요 인원은 h 에 거의 비례한다 — 담당자 확인율이 2배가 되면 인원도 약 2배 필요하다. 그래서 `human_review_surge`(§4.1.2)는 검수 용량 경보이기도 하다. 위 표는 평가 사례에서 잰 h 를 실제 광고 구성이 같다고 보고 쓴 것이다. 문제없는 광고만 보면 h 는 14.7%(34건 중 5건)라 실제 광고에 문제없는 광고가 많다면 필요 인원은 더 크다(`ops/impact.py` 의 `violation_share` 가정이 이 재가중을 한다).

용량이 모자랄 때의 동작: 담당자 확인 건은 *확인 전에는 게재할 수 없다*(`ui/labels.py` 의 안내). 즉 용량 부족은 광고주의 대기 시간으로 이어진다. 대기열의 우선순위(불확실성 표집)와 SLA 는 `ops/review_queue.py` 가 다룬다.

## 10. 처리량 측정 [구현]

`python scripts/loadtest.py --n 500 --warmup 20 --concurrency 1,4 --repeats 3 --seed 0` → `evals/reports/loadtest.json`.
**이 숫자가 의미하는 것:** 모델 호출이 없는 코드 검사와 예시 실행(대역) 파이프라인이 *이 환경*(Xeon 2.1GHz 4코어, Python 3.13, GIL)에서 얼마나 빨리 도는가. 대역은 모델 지연이 없어 *네트워크·모델 지연을 뺀 우리 코드의 처리량*이다.
**의미하지 않는 것:** 실제 모델을 부르는 서비스의 처리량·응답 시간(실제 모델 지연은 사례당 약 3초, 방식 비교에서 따로 잼). 용량 계획에 그대로 쓸 수 없다. 스레드를 늘려도 순수 파이썬 CPU 작업은 거의 빨라지지 않는다.

| 작업 | 스레드 | 초당 처리 건수(중앙값) | 1건 처리 시간 p50 / p95 / p99 (ms) |
|---|---|---|---|
| 코드 검사(`output_guard.check`) | 1 | 591 | 1.34 / 3.78 / 4.92 |
| 코드 검사 | 4 | 535 | 1.69 / 31.4 / 51.8 |
| 예시 실행 파이프라인 1회 | 1 | 42.5 | 24.0 / 37.7 / 48.5 |
| 예시 실행 파이프라인 1회 | 4 | 38.0 | 95.7 / 240.8 / 349.5 |

메모리: 코드 검사는 남은 파이썬 객체 약 14KB 로 일정. 파이프라인은 트레이스를 50개까지 보관해 약 6MB 에서 평탄(뒤 구간 건당 증가량 −628바이트 = 증가 없음), 프로세스 최대 상주 메모리 증가 2.5MB. 이것은 누수가 없다는 증명이 아니라 500회 반복에서 선형으로 늘지 않았다는 점검이다.

한계: 측정 중 다른 프로세스가 CPU 를 쓸 수 있어 적재량을 함께 기록한다(시작 0.40, 끝 0.94). 한 기계·한 번의 측정이다.
